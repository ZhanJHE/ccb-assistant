## 1. 执行摘要

### 总体结论：**良好（下沿）· 综合 3.5/5**

判定理由分三段，缺一不可：

**一、内核确实是优秀的（这部分我给 4.5–5）。** 不是客套，是四个通常最先腐化的地方都被工程化了：

1. **依赖方向不是注释而是测试。** `tests/test_modules.py:34-39` 显式声明允许集，`:109-142` 用 AST 解析真实 import 图，越界即失败；`core` 不 import 兄弟模块、`library` 不 import 网络层，各自还有单独的守卫用例。
2. **三个入口面从一张表派生。** `ops.OPERATIONS` 声明一次（`src/ccb/ops.py:72-395`），CLI/MCP/契约三面派生并互证。实测：`ccb contract` 输出 14 条不变量 / 7 条工作流 / **36** 条命令路径的 `payload_shapes`；`ccb-mcp.py --list-tools` 输出 **16** 个工具 + 5 个 prompt，与 `tests/test_ops.py:55` 的断言一致。
3. **"不编造"被写成可测不变量。** `grounded:false` 不是失败、未测量 ≠ 0、CCF 只给上界与逐条依据（`src/ccb/contract.py:18-112`）；`europepmc` 发现全文链接永久 403 后**删掉伪造的 `pdf_url`**、把 API 声明的链接降级为 `extras.fulltext_urls` 并在 notes 写明这道门（该修复在评审期间由并行会话提交为 `5f5bbd8`，`src/ccb/search/channels/europepmc.py`）。
4. **"文档会漂移"被工程化处理。** `tests/test_docs.py:35-49` 重算 MCP schema 字符数并与 `开发文档/for-agents.md` 比对；`SKILL.md` 渲染后必须 < 8192 字符——过期数字会让测试失败，而不是靠人记得改。

基础事实：`ruff check src tests` 零告警；`python -m unittest discover -s tests` → **360 passed / 23.5s / 无网络**；`ccb doctor` 在真实 787 条语料上 `problems: []`；零必需第三方依赖（`pyproject.toml:14-16`）。

**二、但存在 1 个阻断级安全缺陷，且它就在这条工具最日常的路径上。**

> **S-01（阻断）**：声明式 CLI 渠道在 Windows 上以 `shell=True` 启动 `.cmd/.bat`，并把**用户/agent 提供的 query 直接拼进 argv**（`src/ccb/search/channels/generic.py:443-451, 487-488`；`paper_search.py:108-116` 同形）。我独立复现：`subprocess.run(["echo","search","attention&calc"], shell=True)` 下 `&` 被 cmd.exe 当命令分隔符，第二个命令**确实被执行**。也就是说 `ccb find "attention&<任意命令>"` 或任何走 cli 渠道的 lookup 参数，在本机以用户权限执行任意命令——而本工具的调用方恰恰是会让 LLM 自由构造查询串的 agent。本机 `paper-search` 未安装，故未在真实渠道上触发，但机制与代码路径都已确认。

**三、其余扣分集中在"接缝"与"交付"，模式高度一致：声明面比实现面宽。**

- **本地优先的判据过松（F-10，高）**：本地检索编译成**前缀 OR**（`src/ccb/library/index.py:537-549`），无停用词过滤、无相关度下限。实测 `ccb find "zzz no such topic qqq"`（默认 `-n 10`）→ **10 条本地命中、0 个渠道被查询、`local_answered: true`、exit 0**；`ccb search-local "the of and"` → 5 条。产品最核心的承诺"未命中才上网络"在此失效，而 agent 只看到一个"已答"信号。
- **接口声明 ≠ 实现（F-01/F-02，高）**：`ccb_find` 在 MCP schema 里声明 `stop_after`，处理器从不转发；同一条 `cite`，CLI 支持 8 种格式、MCP 只支持 5 种，而工具描述宣称支持 plain text。
- **凭据声明 ≠ 发送（S-02，高）**：`openalex` 声明 `auth="OPENALEX_API_KEY?"`（`openalex.py:76`）但**全文件不引用该 key**（`search()` 只经 `polite_params` 加 `mailto`，`openalex.py:101-107`）；`paper_search` 同样只声明不发送（`paper_search.py:53`）。而 `ccb channels` 会把它列为 `credentials_present` 并说它"raises the request budget"。用户按报告设置凭据 → 零效果。
- **写入链路不是事务，且自检会绕锁（L2/L3，高）**：`save()` 三步顺序写（`store.py:333-340`）；`index.py:57-62` 只设 WAL + `synchronous`，**没有 `busy_timeout`**——而 `开发文档/模块设计.md:56` 明确写着"`connect` 设 WAL + `busy_timeout=5000`"（文档与代码不符，我已 grep 确认全树无该 PRAGMA）。同文件 `_ensure()`（`index.py:141-151`）在读路径里直接调 `WorkIndex.self_check(repair=True)`→全量 `DELETE`+重插，**绕开了 `Library.self_check/reindex` 上的 `@_serialized` 锁**。
- **首个写操作必然触发全量重建（L4，中，已实测）**：新进程里第一次索引访问若是写路径，`save()` 先落盘再自检 → 指纹必然不匹配 → 全量 reindex。我用计数版 `WorkIndex.reindex` 实测：`merge()` 作为首个动作 → **1 次全量重建**；`search()` 作为首个动作 → 0 次。800 条语料上 `reindex()` 实测 **1.83 s**，即每次"冷启动 + 先写"都白付这笔钱。
- **交付未闭环（F-15/F-16，高）**：`.github/workflows/ci.yml` 声明了 ubuntu/windows × py3.10/3.13 矩阵与 ruff 门禁，但 `origin/main` 只有最初的 58 个文件、**不含 `.github`**，本地 `main` 领先 **42 个提交**——CI 从未执行过，开发史也没有远端备份。同时**缺 LICENSE 文件**（`pyproject.toml:13` 却声明 MIT；仓库已有 GitHub 远端）。

**四、一句话定位**：这是一个**内核质量明显高于平均水平、但把"声明"当成了"实现"的项目**。它已经建立了"把约定变成测试"的能力，却还没有把同样的能力覆盖到"接口声明的兑现"上——测试锁住了「表 ↔ schema」，没锁「schema ↔ 处理器是否真的消费」「文档 ↔ 代码是否真的如此」。

> **使用建议**：在 S-01 修复前，不要让 agent 自主构造查询串走 cli 渠道；在 F-10 修复前，不要把 `local_answered: true` 当作"网上也没有"的证据。

## 3. 结构设计评审（4/5）

### 3.1 分层与依赖方向：优秀

**事实**：四模块 + 共享地板的分层真实存在于代码组织与测试中。

- `core ← library ← search ← topics`，允许集在 `tests/test_modules.py:34-39`；越界即 fail（`:109-124`）。
- `core` 双重保护：`:126-133`（core 不得 import 兄弟）+ `:135-142`（library 不得 import search/topics）。
- 纯/IO 分界也被守：`core/util.py` 纯计算、触盘全在 `core/files.py`，`tests/test_purity.py` 守线（`src/ccb/core/files.py:1-11` 明写"文档字符串里的声明不是边界"）。
- library 层经子代理逐文件核对：10 个文件只 import `core`，无 `library → search` 反向依赖，`resolve()` 不碰网络，全树**只有 `store.py:333` 一处写 work JSON**——单一写路径在"有没有人绕过去"这个意义上是真的。

### 3.2 单一写路径：良好，但原子性不成立

`Library.save()`（`store.py:315-340`）是唯一写入口，顺序为 work JSON（原子替换 + fsync）→ SQLite 索引 → 账本事件。**这不是事务**——详见 §5.2 与 L2/L3/L4。

### 3.3 组件化拆分：良好

`store.py` 从 977 行拆为协调者 + `ledger.py`(85) / `dedup.py`(95) / `fulltext.py`(109)，公共 API 以薄委托保持（`store.py:243-294`）。工作日志诚实记录了拆分脚本两次失败、回滚后手工完成（`开发文档/开发工作日志.md:74-80`）。

**残留**：`store.py` 仍 954 行、`ops.py` 823 行、`cli/_handlers.py` 764 行、`acquire.py` 792 行；功能行数 ≥80 的函数 **16 / 556**，最长 `topics/rating.py:66 rate()` **226 行**（AST 实测）。子代理进一步指出：组件拆到"文件级"而非"接口级"——`Library._archived_event_count` 直转 `self._ledger._archived_event_count`（`store.py:259-260`）、`WorkIndex` 直调 `library._save_meta(...)`（`index.py:321-326`）、`stats()` 自己 `read_jsonl` 绕过 Ledger（`store.py:892`）（L14）。

### 3.4 配置管理：良好，缺集中视图

- 库根优先级链 `--library > $CCB_HOME > $CCB_REPO > checkout 锚定 > cwd`（`core/paths.py:29-53`，`tests/test_paths.py` 15 用例）。
- 凭据只从库内 `credentials.yaml` 读（**注意：已有两处渠道声明了却从不发送，见 S-02**）。
- 渠道可 `papers/channels.yaml` 免代码扩展；CCF 目录是数据（`CCB_CCF_CATALOG` 可整体替换）。
- **缺口**：环境变量散落 7+ 处（`CCB_HOME/CCB_REPO/CCB_CHANNELS/CCB_MAX_EXTRACT_BYTES/CCB_CCF_CATALOG/CCB_PAPER_SEARCH/CCB_MAILTO`），无一处集中列出，`ccb contract` 也不暴露。建议加 `env` 段。
- 子代理发现：`credentials.yaml` / `channels.yaml` 解析依赖**可选** `import yaml` 且异常被吞成 `data=None`（`net.py:203-213`、`registry.py:132-143`）——无 PyYAML 的机器上凭据文件被静默读空，所有 key 渠道报"missing credential"（S-05，本机装了 PyYAML，未能复现，属条件性缺陷）。

### 3.5 错误处理与日志：合格，可观测性不足

`CommandError(message, code, **extra)`（`cli/_context.py:25-32`）→ stderr JSON + 退出码；顶层兜底捕获（`cli/__init__.py:102-110`）。实测退出码符合契约：用法错 `find`→2、`nosuchcmd`→2、`--nope`→2；未找到 `show doi:10.9999/nope`→3；`get ... --offline`→3。

**缺口**：全项目 **0 处 `logging`**；`--verbose` 是空转旗标（F-03）；无请求级耗时/重试/限流等待的度量；失败只能靠账本事后考古（F-14）。

## 4. 接口设计评审（3/5）

### 4.1 契约即接口：优秀

`ccb contract` 返回 14 条不变量、4 个模块的边界与 owns、7 条工作流（每步带 `kind: command|human`）、8 条路由、36 条 `payload_shapes`（实测）。`tests/test_contract.py` 会把每条 `kind: command` 的命令真的解析一遍。

### 4.2 输出形状声明：优秀

`ops.PAYLOAD_KEYS`（`ops.py:652-734`）逐路径声明顶层键，`tests/test_cli.py:417-470` 实跑叶子命令断言"不发出声明外键、干净运行与声明相等"。起因被诚实记录：验证脚本靠猜键名连错四次（`开发文档/开发工作日志.md:87-92`）。

**但形状锁只覆盖部分分支**：`topics survey` 的联网 top-up 会输出 `expansion`（`topics/survey.py:324-325`），而它**未登记进 `ops.PAYLOAD_KEYS["topics survey"]`**（`ops.py:706-709`），`test_cli` 的 `BRANCH_ARGS` 也没有 survey 分支 → 这是形状契约的一个真实缺口（T05，中）。子代理实测：`set(实际输出) - set(声明) == {'expansion'}`。

### 4.3 声明 ≠ 实现：6 处（本维度扣分主因）

**(a) `ccb_find.stop_after` 被静默忽略（高，F-01）**

- 声明 `ops.py:124`（无 `cli_only` → 进 MCP schema）；实测 schema 含 `stop_after`。
- 处理器 `mcp_server.py:147-155` 只传 `limit/channels/year_from/year_to`；CLI 则传了（`cli/_handlers.py:195`）。
- 我用 AST 对全部 16 个 MCP 处理器做了同一审计：**只有这一处**未消费声明参数——纪律总体良好，缺口确实存在且无测试。

**(b) `cite` 两面格式集不一致（高，F-02）**

| `format=` | CLI（实测 exit） | MCP（实测） |
|---|---|---|
| `bibtex`/`ris`/`csl`/`json` | 0 | ok |
| `text` / `plain` / `csl-json` | **0** | **ERROR INVALID_PARAMS** |

CLI 分支 `cli/_handlers.py:312-324`（8 种拼写）；MCP 分支 `mcp_server.py:212-225`（5 种，else 抛错）。而 MCP 工具描述写的是 "BibTeX, RIS, CSL-JSON or **plain text**"（`ops.py:793-795`）——**描述承诺了处理器会拒绝的能力**；报错文案也不含它实际支持的 `json`。

**(c) 全局 `--verbose` 空转（中，F-03）**：声明于 `cli/_parser.py:96,112` 与 `mcp_server.py:568`，贯穿 `Registry/Http/Resolver/Channel` 四个构造器（21 处，全为赋值或透传），**全树无 `if ... verbose` 分支**；实测 `ccb channels` 与 `ccb --verbose channels` 输出逐字节相同。

**(d) `contract.routing` 指向不存在的渠道（中，F-04）**：`contract.py:308` 写 "…then unpaywall…"，`:311` 写 "europepmc, then pubmed"。实际只有 7 个渠道（实测）：`arxiv, crossref, dblp, europepmc, openalex, openreview, paper_search`。实测 `find x -s unpaywall --no-local -n 1` → `warnings: unknown channel name(s) ignored: unpaywall` + `no search-capable channel is currently available`，**exit 0、结果为空**。这违反项目第一条使用规则（"规则从工具取"）——因为工具给的规则本身是错的。

**(e) `find --min-local` 语义与帮助不符（中，F-05）**：声明 `ops.py:123` "only query channels when fewer than N local hits exist"，实现 `acquire.py:489` `len(local_hits) >= max(limit, min_local)`。`min_local=5, limit=10` 时门槛是 10 而非 5；`min_local=0` 时门槛退化为 `limit`。

**(f) `--offline` + `--no-local` 组合（低，F-13）**：实测 offline 分支（`acquire.py:497-504`）在 gate 之后、不再看 `local_first`，故 `--no-local --offline` 仍会做本地查询并返回本地命中。

### 4.4 凭据接口：声明了但从不发送（高，S-02）

- `openalex.py:76` `auth="OPENALEX_API_KEY?"`；该文件**没有任何地方引用这个 key**——`search()` 走 `polite_params`（`openalex.py:101-107`），而 `polite_params` 只加 `mailto`（`base.py:485-487`）。
- `paper_search.py:53` `auth="PAPER_SEARCH_CORE_API_KEY?"`；该文件只把 `dict(os.environ)` 传给子进程（`paper_search.py:104-115`），而 credentials.yaml 的值**不进 os.environ**。
- 与此同时 `registry.py:299-306` 会在设置后把它列进 `credentials_present`，`net.py:79` 附近的说明称其"raises the request budget"。
- 声明式渠道另有一处更细的错：`generic.py:171,182` 用 `not auth.endswith("?")` 直接排除可选凭据，**即使值存在也永不注入**（S-02 的第二形态）。

**影响**：用户按 `ccb channels` 的指引配置凭据 → 零效果、继续吃 429，且没有任何提示。这是"诚实的工具"最不该有的那类静默失效。

### 4.5 能力声明（`caps`/`supports`/`rate_rps`）：声明面宽于实现面（中，S-10/S-11/S-17/T06）

- 6 个渠道把 `"title"`（`paper_search` 还含 `"url"`）写进 `supports`，但 `lookup()` 对这些 scheme 一律返回 error，且 `parse_identifier` 根本不会产出 `"title"` scheme（`arxiv.py:46,86-88`、`dblp.py:46,90-94`、`openalex.py:68`、`openreview.py:45`、`europepmc.py:32`、`paper_search.py:46,184-192`）→ `get "<标题>"` 会跳过全部渠道，最终 `errors={}` 而 message 却说"See errors for which channels were tried"。
- cli/mcp 渠道的 `rate_rps` 完全无效：只有 `spec.hosts` 会进主机速率表（`registry.py:111-123`），`PaperSearchChannel` 既无 `hosts` 也不用自己的 `Http`（`paper_search.py:48-64`）。
- `ChannelResult.queries` 每渠道都在填、`as_dict` 不输出；`KNOWN_HEALTH` 只进报告不参与路由（`registry.py:47-57,280-283`）；`Channel.check()` 无任何子类覆盖、无调用者（`base.py:372-374`）。
- 契约宣称 `gaps` 返回 "empty cells in the method × task × dataset grid"（`contract.py:269-272`），代码无此实现（T06）。

### 4.6 MCP 协议面：良好，少量规范缺口（低，F-07/F-06）

手写 JSON-RPC，`tools/call` 只接受 `ops.BY_MCP` 里声明过的名字（`mcp_server.py:357-358`），批量消息成批返回（`:532-541`），工具异常不杀会话（`:477-482`）。缺口：

- `jsonrpc` 字段不校验——实测 `{"jsonrpc":"1.0",...}` 被当合法请求且成功返回。
- 未知参数静默忽略——实测 `ccb_stats` 传 `{"bogus":1}` 正常返回（无 `additionalProperties:false`，服务端也不校验）。

## 5. 流程设计评审（3/5）

### 5.1 本地优先协议：机制正确，判据错误（高，F-10）

**设计正确**：`needs_metadata` 被显式化为谓词（`acquire.py:175`），并有注释说明"写成条件列表会让 `--with-pdf` 意外覆盖它"。

**判据错误**：本地查询编译为**前缀 OR**：

```python
# src/ccb/library/index.py:537-549
def _fts_query(query: str) -> str:
    """Turn a user query into a safe FTS5 MATCH expression (prefix-OR terms)."""
    tokens = [t for t in "".join(
        ch if ch.isalnum() or ch.isspace() else " " for ch in query).split() if t]
    if not tokens: return '""'
    return " OR ".join(f'"{t}"*' for t in tokens[:12])
```

```python
# src/ccb/search/acquire.py:489-495
if local_first and len(local_hits) >= max(limit, min_local):
    result.local_answered = True
    result.message = (f"Answered from the local library ({len(local_hits)} hits); no "
                      "channel was queried, so nothing was re-downloaded or re-parsed.")
    return result
```

任意 token 前缀命中即算命中，无停用词、无相关度下限，命中数达标就短路整个网络扇出。而 BM25 检索路径（`library/retrieve.py`）**有**停用词处理（`tests/test_retrieval.py::TestTokenizer.test_drops_stopwords_but_keeps_content`）——`Library.search` 这条路径没有，两套检索口径不一致。

实测（真实 787 条语料）：

| 命令 | 结果 |
|---|---|
| `ccb find "zzz no such topic qqq"`（默认 -n 10） | `local_hits: 10`、`local_answered: true`、`channels_queried: []`、exit 0 |
| `ccb search-local "the of and" -n 5` | `count: 5`（纯停用词也命中） |
| `ccb search-local "qqqzzz" -n 5` | `count: 0`（只有无意义单词才为空） |

**修复（建议 1+3）**：① `_fts_query` 改 AND + 前缀；② 复用 `retrieve.py` 的停用词表，消除两套口径；③ 输出 `score` 并让调用方自行判断；④ `find` 的短路策略改为显式（如"命中数 ≥ limit 且最高分 ≥ 阈值"）。

### 5.2 事务与一致性：良好设计，缺口在三处（高/中）

**事实**：`save()` 三步顺序写（`store.py:333-340`），自愈机制真实存在（`index.py:162,243` 用文件指纹 + 账本事件数交叉校验），实测 `doctor` 在 787 条语料上 `problems: []`。

**缺口**：

1. **无两阶段提交（L2，高）**：`index_work` 抛 `OperationalError`（`database is locked`）时异常穿透，留下"记录在盘、索引与账本缺失"的状态；账本缺行只被**报告**、永不修复（`index.py:243-252`）。而 `index.py:57-62` **没有 `busy_timeout`**（与 `开发文档/模块设计.md:56` 的声明矛盾），使这个窗口更容易被撞上。
2. **自检绕锁（L3，高）**：`_ensure()`（`index.py:141-151`）在读路径里直接调 `WorkIndex.self_check(repair=True)` → 全量 `DELETE FROM works/ids/aliases/blocks` + 重插，**不经过** `Library.self_check/reindex` 的 `@_serialized`（`store.py:399-412`）。两个进程一个写一个读时，可在无锁状态下与持锁写方交错。
3. **冷启动先写必触发全量重建（L4，中，已实测）**：`save()` 先写 JSON 再由 `index_work` 触发首次 `_ensure()`（`index.py:330-335`），此时 `self_check` 拿"刚被本进程改写"的文件比 meta 指纹（`index.py:213-216`）→ 必定漂移 → 全量 `reindex()`。实测：新进程首个动作是 `merge()` → **1 次重建**；首个动作是 `search()` → 0 次。800 条语料 `reindex()` = **1.83 s**。
4. **合并半途失败可致记录复活（L1，高）**：`_absorb` 与 `merge` 把 unlink 失败 `except OSError: pass` 吞掉（`store.py:644-647`、`768-772`），紧接着 `deindex_work` 删索引行、账本无条件记 `removed_path`/`merge`（`:651-654`、`:776-777`），`merge()` 仍返回 `{"merged": True}`。若旧文件删不掉：文件数 ≠ 索引行数 → 下次自检重建 → 已被合并掉的论文**作为独立记录复活**，同时其 id 又留在 `keep.aliases` 里 → `count()/stats()/export/ask` 出现重复。对照 `reidentify` 的处理是**正确**的（`store.py:447-451` 会记 `stale file kept`）。
5. **临时文件会被当成 work 文件（L5，中，已实测）**：`WORK_FILE_GLOB = "**/*.json"`（`index.py:30`）会匹配原子写残留的 `.tmp-*.json`（`files.py:29` 用 `prefix=".tmp-"`）——我实测 `pathlib.glob("**/*.json")` 与 `fnmatch(".tmp-abc.json","*.json")` 都为 True。而 `self_check` 按**文件数**计、按**索引行数**比（`index.py:182-183, 223-225`），一次崩溃留下的临时文件就能让每个新进程都全量重建，甚至被 `all_work_ids()` 的兜底塞进假 id。
6. **schema 版本字段只写不读（L6，中）**：`LIBRARY_SCHEMA`/`key_chain_version`/`KEY_CHAIN_VERSION`/`WorkRecord.schema` 全树无任何比较或迁移派发（`store.py:62,185-191`、`ids.py:141`）→ `src/ccb/AGENTS.md` 的"改磁盘格式 = 迁移 + 测试"在代码里没有落点。

def _fts_query(query: str) -> str:
    """Turn a user query into a safe FTS5 MATCH expression (prefix-OR terms)."""
    tokens = [t for t in "".join(
        ch if ch.isalnum() or ch.isspace() else " " for ch in query).split() if t]
    if not tokens:
        return '""'
    return " OR ".join(f'"{t}"*' for t in tokens[:12])
