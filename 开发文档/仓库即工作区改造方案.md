# 仓库即工作区（repo-as-workspace）改造方案

- 状态：**草案 v0.2，待确认后再动代码**
- 适用范围：`lit`（本仓库 `ccb-assistant`）
- **已定决策**
  1. 数据根 = 仓库内**可见的 `papers/`**（不再是隐藏的 `.lit/`）
  2. **Git 只跟踪开发产物**（代码、测试、开发文档、skill）；**使用期产生的一切数据全部只放本地，不进仓库** —— 语料、JSON、账本、快照、全文、PDF 一视同仁
  3. 先方案后代码；`tools/lit-skill.py` 直接删

---

## 0. 一句话目标

把这个仓库从「一个可以 `pip install` 到系统、或作为 skill 软链到 `~/.dsh/skills/` 的工具」，改成 **clone 下来就是文献工作台**：

> 代码、开发文档、以及你使用过程中产生的论文 PDF / 元数据 JSON / 课题产物，**在同一个目录里**。
> Git 是开发用的（只管代码）；这个目录同时是你的数据目录，不安装、不配置、不指定路径，`cd` 进来就能用。

harness（DSH）只是**恰好从这个目录调用它**的宿主，不再定义它的分发方式。

## 2. 现状错位（都有代码证据）

### E1 库根按 `cwd` 解析，不按仓库解析 —— 直接违背目标

`src/lit/library/store.py:107-113`：

```python
def default_library_root(cwd: Path | None = None) -> Path:
    """Resolve the library root: ``$LIT_HOME`` wins, then ``<cwd>/.lit``."""
    env = os.environ.get("LIT_HOME")
    if env:
        return Path(env).expanduser()
    base = Path(cwd) if cwd else Path.cwd()      # ← cwd，不是 checkout
    return base / DEFAULT_LIBRARY_DIRNAME
```

调用点：`src/lit/cli.py:59`、`src/lit/mcp_server.py:337`。

后果：harness 的 cwd 是**使用者的项目目录**。`python <repo>\lit.py find "..."` 下载的论文会落到**那个 cwd** 的 `.lit/` 里，不在仓库目录里。"clone 到这个目录"和"数据落在这个目录"目前是两件事 —— 在哪调用，数据就长在哪。

> 本会话恰好 cwd == 仓库根，所以那个 `.lit/` 看着像"就在目录里"，那是巧合，不是机制。

### E2 数据藏在 `.lit/`，用户根本看不见自己的库

`.gitignore:18-23` 排除 `.lit/` —— **这一条在新决策下是正确的、保留**。真正的问题不是"被排除"，而是：

- **点号开头**，文件管理器与 `ls` 默认不显示 → 使用者感知不到自己的语料在哪、有多大；
- **锚在 cwd**（E1）→ 目录会跟着调用位置乱跑，同一个仓库能长出好几份库；
- 文档里的示例（README、SKILL.md）早已用 `--library ./papers`，**只有代码的默认值没跟上**。

### E3 文档叙事全部指向"可分发插件"

- `README.md:67-96` 开头是 `pip install -e .`；`README.md:220-223` 教你复制/软链到 `~/.dsh/skills/`
- `.dsh/skills/lit/SKILL.md:27` 让 agent 用 `/path/to/tools/lit-skill.py`
- `.dsh/skills/lit/references/commands.md:11-18` Setup 段同上

三处都在暗示"工具装在系统里、数据在别处"。

### E4 被新决策推翻的既有论证（必须改，否则文档自相矛盾）

- `docs/design.md:316` 与 `.dsh/skills/lit/references/architecture.md:75-77` 把"**可提交进 git**"列为"纯文本为真相源"的理由之一。数据只放本地后，这条理由作废；其余理由（可 diff、可 grep、可被 agent 直接读、可手工改、`index.sqlite` 删了能重建）**仍然成立**，需重写这段。

## 3. 目标形态

### 3.1 目录树

```
ccb-assistant/                    ← git clone 下来就是这个，cd 进来即用
  lit.py  lit-mcp.py              ← 入口，免安装
  src/  tests/  tools/  docs/  notes/   ← ← ← git 跟踪的部分到此为止
  .dsh/skills/lit/                ← 让 harness 在这个目录里发现它
  papers/                         ← ★ 你的文献工作区（本地数据，不进 git，首次运行自动创建）
    library.json                  ← 库元信息 + schema 版本
    library.jsonl                 ← 只追加审计流水
    works/<2>/<2>/<work_id>.json  ← 权威记录：身份 + claims + manifestations
    evidence/<ev_id>.json         ← 渠道原始响应快照
    channels.yaml                 ← 可选：不写代码声明额外渠道
    topics/                       ← 课题产物（surveys/candidates/records/drafts）
    files/<2>/<sha256>.pdf        ← 论文 PDF（内容寻址）
    blobs/<work_id>/fulltext.txt  ← 抽取出的全文
    blobs/<work_id>/passages.json ← 段落索引（派生）
    index.sqlite                  ← 查询索引（派生）
```

`papers/` 会自动出现：`Context.__init__` 调用 `library.ensure()`（`cli.py:61`），所以**连 `lit channels` 都会创建它**。不需要 `.gitkeep`，也不设任何 git 例外。

### 3.2 产物分类：决定"能不能重建"，不决定 git

分类仍然有用（决定哪些文件可以放心删、哪些是唯一副本），但 **git 策略对四类统一为：不进仓库**。

| 类别 | 路径 | 能否重建 | 唯一副本？ | 进 git |
|---|---|---|---|---|
| **真相源** | `library.json`、`library.jsonl`、`works/**`、`evidence/**`、`channels.yaml`、`topics/**` | ❌ 重建不出（身份链与 provenance 是计算产物但不可从别处还原） | ✅ | ❌ |
| **可读全文** | `blobs/**/fulltext.txt` | 能从 PDF 重抽（但 PDF 需重新下载） | 半 | ❌ |
| **派生** | `blobs/**/passages.json`、`index.sqlite*` | ✅ 随时重建（`store.py:854-882` 自愈；`lit index`/`lit repair`） | ❌ | ❌ |
| **二进制** | `files/**/*.pdf` | 能从渠道重新下载 | 半 | ❌ |

> 实践含义：**`papers/` 是你的唯一数据副本**。要备份就整个目录拷贝；要换机就整个目录搬。派生件删了无所谓，`works/` 与 `files/` 删了就真没了。这一条要写进 README。

### 3.3 clone 之后是什么状态（新决策下重写）

全新 clone = **空库 + 可用的工具**。语料从零开始，在你自己的机器上长出来。

| 命令 | 全新 clone（无 `papers/`） | 正常库 |
|---|---|---|
| `channels` / `contract` | ✅ 并创建空 `papers/` | ✅ |
| `doctor` | ✅ 报空库 | ✅ |
| `find` | ✅ 走渠道联网（本地无命中） | ✅ 本地优先，零网络 |
| `get --with-pdf` | ✅ 下载 → 落进 `<repo>/papers/` | ✅ 幂等，已在库中则零网络 |
| `open` / `ask` | ⚠️ 空库 → 必须给出友好提示（AC5），而不是 `grounded: true` 的假象 | ✅ 读本地全文；`ask` 的段落索引缺失时自愈重建 |
| `cite` / `export` / `show` | ✅ 空结果 | ✅ 纯本地 |
| `topics *` | ✅ 但语料不足会报 `sufficient: false`（设计如此，不硬凑） | ✅ |

## 4. 改动设计

### D1 库根解析链：从 cwd 锚定改为 checkout 锚定（**本次改造的核心**）

新增 `src/lit/core/paths.py`（`core` 层，只用标准库，不 import 任何自家模块，不违反 `tests/test_modules.py` 的 DAG）：

```python
def checkout_root(start: Path | None = None) -> Path | None:
    """The clone directory, if the running code lives inside one.

    Returns None for a site-packages install, which is what makes the cwd
    fallback safe rather than surprising.
    """
    start = (start or Path(__file__)).resolve()
    for base in (start, *start.parents):
        if (base / "src" / "lit" / "cli.py").exists() and (base / "lit.py").exists():
            return base
    return None
```

`default_library_root` 改为（`library → core` 的依赖方向本来就存在，`store.py:31-42` 已在用 `..core.*`）：

```python
DEFAULT_LIBRARY_DIRNAME = "papers"      # 原 ".lit"

def default_library_root(cwd: Path | None = None) -> Path:
    env = os.environ.get("LIT_HOME")
    if env:
        return Path(env).expanduser()
    repo = os.environ.get("LIT_REPO", "").strip()
    if repo:
        return Path(repo).expanduser() / DEFAULT_LIBRARY_DIRNAME
    found = checkout_root()
    if found is not None:
        return found / DEFAULT_LIBRARY_DIRNAME
    return (Path(cwd) if cwd else Path.cwd()) / DEFAULT_LIBRARY_DIRNAME
```

优先级：`--library` > `$LIT_HOME` > `$LIT_REPO` > **checkout 锚定** > `<cwd>` 兜底。
`cwd` 形参保留（测试在用），语义不变。

### D2 默认目录名 `.lit` → `papers`

一处常量（`store.py:67`）+ 全部文案。`papers` 不是新发明的名字 —— README 与 SKILL.md 的示例已经用它，这次只是让代码跟上。

### D3 启动器去重：三份 → 两份

现状三份启动器都在做同一件事（找 `src/`）：`lit.py`、`lit-mcp.py`、`tools/lit-skill.py`，外加 `.dsh/skills/lit/lit.py`。

- 保留 `lit.py`（CLI 主入口）与 `lit-mcp.py`（MCP 入口）—— 免安装，符合本模型。
- 保留 `.dsh/skills/lit/lit.py` —— 它服务"skill 被复制到 `~/.dsh/skills/` 后仍能找到 checkout"这一种情形（靠 `LIT_REPO` / 同级目录）。
- **删除 `tools/lit-skill.py`**，文档统一指向 `<repo>/lit.py`。
  （已入库文件用 `git rm` 移除，历史可追回，不走文件系统删除。）

### D4 工作区说明写进根 README，数据目录不设 git 例外

**不新增 `papers/README.md`** —— 那需要 `!papers/README.md` 反向例外，会给"数据目录里有什么能进 git"开一个先例。改为在根 `README.md` 里写一节"你的工作区在 `papers/`"，说明：首次运行自动创建、整体不进 git、是唯一数据副本、备份方式、`git clean` 风险。

`lit` 首次运行自动建目录（`ensure()`），所以"clone 后看不见 `papers/`"只是一次命令之内的事。

### D5 空库与缺文件时的措辞（缩小版）

v0.1 把这条当成"必须配套的大改"，因为当时 clone 会带来"记录说缺 PDF"。**数据不进 git 后，那个场景消失了**：记录与 PDF 永远同时产生于同一台机器。所以这里只剩两处体验改进：

1. **空库友好**（AC5）：`open`/`ask`/`show`/`cite` 在库为空时，输出里应给出明确下一步（`lit find` → `lit get --with-pdf`），而不是空结果或异常。`cli.py:325-335`、`retrieve.py:82-89` 已有类似提示，需确认覆盖所有入口并加断言。
2. **`extract` 的失败信息**：`has_pdf()` 是记录级判断（`core/model.py:340-341`），若文件被人为删掉，`cli.py:598` 会对不存在的路径调用抽取器。改为先检查文件存在，给出 `lit get <id> --with-pdf` 的指令式错误。

`check-files` 的 `missing` 语义**保留**（本地模型中文件缺失确实是异常），只在输出里补一句修复提示。

### D6 `_config_paths` 的 cwd 依赖一并处理

`cli.py:84-90` 现在查 `<library>/channels.yaml` 与 `Path.cwd()/lit-channels.yaml`。补一条 `checkout_root()/lit-channels.yaml`，让"仓库即工作区"下配置文件也能就位；cwd 那条保留（向后兼容）。
