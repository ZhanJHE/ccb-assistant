# 选题 2：小 FPGA KV 协处理器（KV-Acc）

**暂定标题**：*KV-Acc: An Off-Path FPGA Co-processor for KV-Cache Compression and Block Management in Resource-Constrained LLM Serving*

## 一、研究背景

### 1.1 KV Cache：从"显存问题"到"数据移动问题"
LLM 自回归解码时，每个 token 都要缓存其 Key/Value 向量，随上下文长度与并发数**线性增长**，是显存的主要消耗者（PagedAttention/vLLM, SOSP 2023，[arXiv:2309.06180](https://arxiv.org/abs/2309.06180)）。

随着 PD（prefill/decode）分离架构成熟（DistServe [arXiv:2401.09670]、Mooncake [arXiv:2407.00079](https://arxiv.org/abs/2407.00079)），KV Cache 不再只待在一块 GPU 里，而要在 **GPU HBM → CPU DRAM → SSD / 跨节点网络**之间反复移动，由此产生三类新操作：
1. **压缩/反压缩**：低比特量化（KIVI 2-bit, [arXiv:2402.02750](https://arxiv.org/abs/2402.02750)）、稀疏驱逐（H2O, [arXiv:2306.14048](https://arxiv.org/abs/2306.14048)）；
2. **块管理**：block table 映射、gather/scatter、碎片整理；
3. **格式重排/打包**：把压缩后不规则的 KV 打包成连续传输格式（SpectrumKV [arXiv:2606.08635](https://arxiv.org/abs/2606.08635) 提出按 token 混精度，但只有软件 timing）。

**关键观察**：这些操作是**数据量中等、逻辑规则、低精度/整型友好、可高度流水**的，却被放在 GPU（占用其宝贵的显存带宽与调度槽）或 CPU（受限于缓存与标量性能）上执行。它们是专用硬件的理想负载——这就是 KV-Acc 的切入点。

### 1.2 现有 FPGA LLM 工作的"盲区"
| 工作 | 用的器件 | 做了什么 | 留下的空白 |
|---|---|---|---|
| FlightLLM（FPGA 2024，[arXiv:2401.03868](https://arxiv.org/abs/2401.03868)） | 数据中心 U280/VHK158（HBM、9024 DSP） | 完整 LLM mapping flow，含矩阵乘主算力 | 依赖昂贵数据中心大卡；**没有专门的 KV 压缩/管理协处理器** |
| CXL-SpecKV（FPGA'26 Oral，[arXiv:2512.11920](https://arxiv.org/abs/2512.11920)） | 数据中心 FPGA + **CXL 互连** | 推测预取 + KV 压缩引擎 | 需要 CXL 与大器件；**普通以太网/低成本小板的旁路方案没人做** |
| HillInfer（[arXiv:2602.18750](https://arxiv.org/abs/2602.18750)） | SmartSSD（计算型存储） | 把轻量 token importance 评估放到近存储 FPGA | 用的是**启发式** importance；**学习型 block 预测 + 独立小板**未做 |
| PD-Swap（[arXiv:2512.11550](https://arxiv.org/abs/2512.11550)） | 边缘 FPGA | 用 DPR 在 prefill/decode 逻辑间切换 | 不做 block 压缩/管理 |

**结论**：用一块**最小、最便宜、普通接口的 FPGA**，专门只做"KV 压缩 + 块管理"这一窄而深的协处理器，是文献中尚未被占据的点。

## 二、目标硬件的真实能力（已核实，决定设计边界）

### 2.1 XC7A35T 芯片资源（Xilinx DS180 / Artix-7 product table 标准值）
| 资源 | 数量 | 说明 |
|---|---|---|
| Logic cells | 33,280 | 极小 |
| CLB LUTs | 20,800 | |
| CLB FFs | 41,600 | |
| **DSP48E1** | **90** | 修正调研稿"约50个"的低估 |
| **Block RAM** | **50 × 36 Kb = 1.8 Mb ≈ 225 KB** | 片上存储很小 |
| 外部存储 | 板载 DDR3（约 512 MB，以具体板为准） | 带宽 ~10 GB/s 量级，远低于 HBM |

对比：FlightLLM 的 U280 有 ~1.3M LUT、9024 DSP、HBM——**35T 的 LUT/DSP 约为 U280 的 1/50~1/100**。

### 2.2 达芬奇开发板接口（关键约束）
- **以太网：10/100 M（LAN8720 PHY），峰值 ≈ 12.5 MB/s**（正点原子《达芬奇 FPGA 开发指南》第 47 章以太网实验对应硬件）。**不是千兆**。
- 有 USB、HDMI、扩展 IO；**没有把 FPGA 直接接到 GPU 主机 PCIe 的通道**。

> **这个 100M 网口是整个选题最大的工程约束，必须正面处理（见 3.3）。**
>
> **限定条件（增补后）**：本节 2.1/2.2 的资源上限与 100M 网口约束，是"坚持用个人 Artix-7 小板"方案下的边界；实验室 **XCVU13P** 方案（PCIe Gen3 x16 直连主机、12,288 DSP、≈57 MB 片上存储）不适用本节结论，见增补第 3 节。

## 三、系统设计

### 3.1 设计原则：off-path（旁路）+ asynchronous（异步），绝不阻塞 GPU
由于 100M 带宽比真实 KV 流量（数据中心网卡 100~400 Gbps）低 3 个数量级，**FPGA 绝不能串在 GPU 的关键路径上做内联压缩**。正确定位是：

> **一块旁路、异步的"KV 压缩/管理服务引擎"**——GPU/主机把"冷"的、不急于使用的 KV 块发给它，它在后台完成压缩/打包/打分，再异步回传结果或写入存储。**它慢，但因为只处理对延迟不敏感的冷数据，慢不影响主推理。**

### 3.2 四个硬件模块（每个都窄而深、35T 可综合）
1. **流式 KV Codec（核心，最稳）**
   - 数据通路：FP16 → INT8/INT4 的流式量化 + 打包；反向反量化。
   - 对齐 KIVI 的非对称方案：**Key 按 channel、Value 按 token**，避免分组（per-group）量化带来的复杂归约。
   - 纯整型、可深度流水，90 个 DSP 足够做缩放/偏移。
2. **Block Table 管理单元 + Gather/Scatter DMA**
   - 在 BRAM/DDR3 中维护逻辑块→物理块映射；处理压缩后不规则块的整理与连续打包。
3. **学习型 Block 重要性选择器（亮点，接上你的项目）**
   - 把你做过的 MLP predictor **蒸馏/量化为整数小网络**（或退一步用硬件 top-K/heavy-hitter 排序器），异步给每个块的"剩余访问价值"打分，决定压缩精度与驱逐顺序。
   - HillInfer 用启发式，你用学习型——这是差异点。
4. （可选）**RoPE / 在线 softmax 近似**单元：查表/分段线性。

### 3.3 三层评估方法（绕开"小板带宽太低"的质疑）
论文的说服力不依赖"在 100M 板上跑真实大流量"，而靠三层互相印证：
1. **RTL 级实测（硬件真实性）**：在 35T 上综合，报告每个模块的 LUT/FF/DSP/BRAM 占用、最高频率、**Codec 与选择器的每周期吞吐（处理 KV 元素/周期）**——用微结构吞吐证明"该引擎在高速时钟下能达到数据中心所需的有效带宽"。
2. **Trace-driven 端到端仿真（系统收益）**：复用你已有的 vLLM trace（317 K 事件），把 FPGA 的处理延迟/吞吐参数代入，仿真接入后对**字节传输量、压缩率、命中率、TTFT、p99** 的影响。
3. **小规模真机闭环（落地证据）**：100M 链路上 FPGA 与主机真实收发压缩 KV，跑通"主机→FPGA 压缩→回传→vLLM 解包使用"全流程（速率不是重点，功能闭环才是）；大模型侧短期租 1×4090 验证。

### 3.4 论文的三个贡献（claim）
1. 首个面向**资源极小 FPGA**、只做 KV 压缩与块管理（不碰 GEMM）的协处理器微结构；
2. **学习型 block 重要性 → 混合精度压缩**的硬件高效实现（区别于 HillInfer 启发式）；
3. "旁路异步 + 压缩-传输重叠"的协同模式，以及在真实 vLLM trace 上的端到端收益。

## 四、可行性分析（诚实评估）

### 4.1 可行的理由
- **能力完全匹配**：你手写过 RISC-V CPU（具备完整 RTL/仿真/综合能力），又做过 KV 驱逐策略（懂算法与 vLLM 内部）——这个选题几乎是为你的技能栈量身定的。
- **资源够**：单个 Codec 模块预计只需数千 LUT + 十几个 DSP，35T 装得下；做 2-3 个模块没问题。
- **省钱**：硬件你已有，只需短期租 1×4090（预算内）。
- **新颖性安全**：与 CXL-SpecKV（CXL+大卡）、HillInfer（启发式+SmartSSD）差异明确。

### 4.2 主要风险与对策
| 风险 | 严重度 | 对策 |
|---|---|---|
| **审稿人质疑"100M 板根本不现实"** | 高 | 论文定位为"微结构 + co-design 洞察"，用 (a) 综合后每周期吞吐外推到高速时钟、(b) trace-driven 端到端收益说话；标题/场景强调 *resource-constrained / edge-assisted*，弱化"替代数据中心卡" |
| **35T 资源装不下"学习型选择器"** | 中 | 先只保 Codec + Block Table 两个最稳模块；学习型选择器做简化整数版，作为加分项而非必需 |
| **FPGA 与 GPU 主机只能走 100M 网，真机闭环慢** | 中 | 真机只验证功能正确性，性能结论全部来自 RTL 微基准 + trace 仿真；不把真机速率写进结论 |
| **learned eviction 赛道已有 KVP/KVLearn** | 中 | 本选题卖点是"**硬件微结构 + 压缩**"而非"驱逐算法新"，算法只作组件，需在论文显式区分 |

### 4.3 投稿场馆（2022 CCF 分级，已核准）
- **CCF-B**：会议 **FPGA**（FPGA 领域顶会）、**ICCD、DATE**；期刊 **ACM TACO、ACM TOS**。
- 保底 CCF-C：FCCM、FPL、FPT。
- **建议**：若担心审稿人质疑平台，优先 **ICCD / DATE**（接受"小器件实现 + co-design"类工作）或 **TACO**（重微结构与编译器洞察）；FPGA 会议竞争更激烈、更看重与 GPU 的正面对比。

### 4.4 8 个月里程碑
- 10-11 月：trace 框架接入 Codec 时序模型；RTL 实现 FP16↔INT8/INT4 Codec 并仿真。
- 12 月：CodeC 综合到 35T 出资源/频率数据；Block Table 单元。
- 1-2 月：学习型选择器整数化（可选）；100M 以太网 UDP 收发 + 真机功能闭环。
- 3 月：租 4090 做 vLLM 端到端验证，补齐 trace 数据。
- 4 月：写作投稿。

## 五、一句话判断
**技术上完全可行、与你能力高度匹配、新颖性安全；唯一需要精心经营的是"如何回应 100M 小板平台不现实"的质疑**——用"微结构吞吐 + trace 端到端 + 功能闭环"三层论证，并选对 ICCD/DATE/TACO 这类场馆即可化解。

# 选题 4：RK3588 NPU × KV 换页联合调度（EdgeKV）

**暂定标题**：*EdgeKV: Joint NPU Offloading and KV Swapping for Long-Context LLM Inference on a Mobile SoC*

## 一、研究背景

### 1.1 端侧长上下文的两难：decode 带宽墙 + NPU 不匹配
在 RK3588 这类移动 SoC 上跑长上下文 LLM，同时撞上两堵墙：
1. **内存带宽墙**：RK3588 是 64-bit LPDDR4X，理论峰值 ~34 GB/s，**STREAM 实测仅 21–22 GB/s**（LPDDR4X-2112 出货板 NEON load 仅 16.9 GB/s）（出处：[Turing Pi RK1 Benchmarks](https://turingpi.com/rk1-benchmarks/)、[Radxa tinymembench Gist](https://gist.github.com/RadxaStephen/88b6a5e09699017d04a2299192104232)）。decode 阶段每生成一个 token 都要把全部 KV 过一遍，速度被带宽锁死。
2. **NPU 与 LLM 动态特性不匹配**：llm.npu（"Panda"，ASPLOS 2025，[arXiv:2407.05858](https://arxiv.org/abs/2407.05858)）实测 NPU 三大限制：
   - 只支持**静态 shape**（变长 prompt 要重编译图，Gemma-2B 图优化 11.54 s）；
   - **不支持 per-group MatMul**（分组量化需拆子矩阵 + 浮点归约，开销 8.1–10.7×）；
   - **浮点极弱**（FP16 MatMul 比 INT8 慢百倍），而 LayerNorm/softmax 离不开浮点。

由此得到一个被反复验证的结论——**"NPU 强 prefill、CPU 强 decode"**（另见测量论文 [arXiv:2607.05475](https://arxiv.org/abs/2607.05475)）。

### 1.2 两条最新主线，还没有人把它们连起来
- **主线 A：NPU offload 优化 prefill**——llm.npu 让 1B 模型 prefill >1000 t/s、平均快 22.4×，但它**不解决 decode 的 KV 容量问题**。
- **主线 B：KV 换页/分层到闪存**——
  - KVSwap（SenSys 2025，[DOI:10.1145/3745756.3809234](https://doi.org/10.1145/3745756.3809234)）：磁盘感知分组换页 + 低秩 key 摘要预测重要性 + rolling buffer；
  - mzCache（MobiCom 2026，[arXiv:2609.01338](https://arxiv.org/abs/2609.01338)）：多任务内存压力下弹性驱逐；
  - TierKV（[arXiv:2609.21172](https://arxiv.org/abs/2609.21172)）：prefill hidden state 预测，分到 exact/低秩/flash 三层。
  - **但这些换页工作都没有利用 NPU**，I/O 与计算各自为政，decode 时仍有 I/O 停顿气泡。

> **空白**：让 **NPU 跑 prefill/静态线性层的同时，CPU/UFS 异步完成下一批 KV 的量化、换出与预取**，把 I/O 完全藏进 NPU 计算时间——两者的联合调度至今没有成熟方案。

## 二、RK3588 能力画像（已核实）

### 2.1 跑 LLM 实测性能
**CPU（llama.cpp，llama-bench，4 线程，[GGUF benchmark](https://turingpi.com/llm-inference-benchmarks-rk3588-gguf-quantization/)）**：
| 模型 | 量化 | 生成 t/s |
|---|---|---|
| Qwen2.5-1.5B | Q4_K_M | **22.57** |
| Llama-3.2-3B | Q4_K_M | 11.25 |
| Qwen2.5-7B | Q4_K_M | **5.44** |

**NPU（RKLLM 官方 benchmark，[GitHub](https://github.com/airockchip/rknn-llm/blob/release-v1.3.0/benchmark.md)）**：
| 模型 | W8A8 t/s | TTFT(ms) |
|---|---|---|
| Qwen2-0.5B | 41.58 | 145.9 |
| Qwen2.5-1.5B | 16.69 | 378.3 |
| ChatGLM3-6B | 4.98 | 1352.9 |

> 注意：RK3588 RKLLM **仅开放 W8A8**（W4A16 只在 RK3576）；NPU 的 W8A8 与 CPU 的 Q4 不同精度、不能直接比 t/s。

### 2.2 功耗/温度（[Turing Pi](https://turingpi.com/rk1-benchmarks/)）
空闲 4–5 W、CPU+内存满载 10–12 W；稳态 66–74 ℃，>80 ℃ 降频。这使"能耗"成为一个有价值的评测维度。

### 2.3 NPU 对 KV 操作的限制（决定哪些能上 NPU）
- 动态 KV 驱逐/换页/稀疏 gather 是**数据相关**操作，无法表达成静态 NPU 图，**只能在 CPU 侧做**；
- NPU 算子不支持即**回退 CPU**，频繁回退 + 同步会吃掉 offload 收益（可造成 ~40% 能耗浪费）。

## 三、系统设计

### 3.1 核心架构：阶段分工 + I/O-计算流水线
```
Prefill 阶段 → 主要丢给 NPU（其强项，chunk-sharing 静态图）
Decode  阶段 → CPU 主导（GEMV + 动态 KV 操作）
冷 KV 块     → CPU 异步量化/换出到 UFS；按需预取
联合调度器   → 把 KV 的 I/O 编排进 NPU/CPU 计算的气泡里
```

### 3.2 三个技术贡献
1. **NPU×KV 换页联合调度器**：在 NPU 执行静态 chunk 线性层的同一时间窗，CPU 并行做下一批 KV 的量化打包、UFS 换出/预取，消除 I/O 停顿（这是 KVSwap 与 llm.npu 都没做的核心点）。
2. **存储感知 + 重要性感知的块放置**：用真实 UFS 延迟/带宽（而非假设）做布局，结合轻量重要性预测（可复用你 KV 项目的特征思想）决定换出谁、用什么精度、何时预取。
3. **最小侵入式集成**：在 RKNN/RKLLM 的 W8A8、静态图限制下，通过自定义调度层而非改 NPU 图来实现。

### 3.3 评估（硬件全免费）
- **性能**：Qwen2.5-1.5B / 7B 的 prefill t/s、decode t/s、TTFT、支持的最大上下文长度（长上下文是核心卖点）。
- **基线**：纯 CPU（llama.cpp）、NPU-only（RKLLM）、KVSwap 式换页、**本方案联合调度**。
- **能耗**：整机功耗（空载 4-5W / 满载 10-12W 为参照）与每 token 能耗。
- **精度**：LongBench / RULER 上的质量损失，验证换页 + 压缩近无损。

## 四、可行性分析（诚实评估）

### 4.1 可行的理由
- **硬件现成、零成本**：RK3588 就在手边，所有实验免费，可反复测，不依赖租卡（最省钱的选题）。
- **空白明确**：KVSwap/llm.npu 两条主线的交叉点确实没人做，差异一句话能讲清。
- **数据基础扎实**：llm.npu、KVSwap、mzCache 都是 2025-2026 新论文，路线清晰、可直接对标。
- 导师方向含**边缘智能**，属于其指导范围。

### 4.2 主要风险与对策
| 风险 | 严重度 | 对策 |
|---|---|---|
| **端侧 KV 系统 2026 集中爆发，撞车风险上升** | 中高 | 尽快锁定"**换页 × NPU 协同**"这个最具体的交叉点；动手前再扫一轮 arXiv，确认无人占位 |
| **RKLLM 闭源、可控性差**，难以把调度插进 NPU 执行 | 高 | 用"**NPU 当黑盒执行 chunk + CPU 侧调度层包一层**"的方式，不依赖改 NPU 内部；必要时 prefill 用 CPU/GPU 路径做对照 |
| **I/O 可能本来就藏不住**（UFS 太慢） | 中 | 先做一个 2 周的 profiling spike：实测 UFS 读写延迟与 NPU chunk 计算时间，确认有重叠窗口再全面投入 |
| 收益可能有限（带宽墙决定上限） | 中 | 把卖点放在"**支持更长上下文 + 单位能耗**"而非"绝对 t/s"；长上下文可用性本身就是贡献 |

### 4.3 投稿场馆（2022 CCF 分级，已核准）
- **CCF-B**：会议 **SenSys、MobiSys**（边缘顶会，竞争激烈）、**ICDCS、ICPP、Euro-Par**；期刊 **Computer Networks、TNSM**（更稳、导师有 COMNET 经验）。
- CCF-C 保底：ICPADS、MobiQuitous。
- **建议**：求稳投 **Computer Networks**（导师熟、rolling）；若系统做得漂亮、含完整能耗实测，可冲 **SenSys/MobiSys**。

### 4.4 8 个月里程碑
- 10 月：先做 profiling spike（UFS 延迟 × NPU chunk 时间），确认重叠窗口。
- 11 月：RK3588 上复现 Qwen2.5-1.5B/7B 的 CPU/NPU 基线。
- 12-1 月：实现 CPU 侧 KV 换页 + 预取，做存储感知布局。

- 3 月：性能/能耗/精度全面评测。
- 4 月：写作投稿。

## 五、一句话判断
**最省钱、硬件零成本、空白明确，且在导师边缘智能指导范围内；最大不确定性是 RKLLM 闭源导致的"调度能否真正插进 NPU"以及 I/O 重叠窗口是否足够**——因此**强烈建议第一步先做一个两周的 profiling spike**，用实测数据确认前提成立，再全面投入。
