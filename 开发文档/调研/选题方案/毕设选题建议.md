## 0. 约束条件（决策前提）
- **时间窗**：2026-09 ~ 2027-05（约 8 个月），答辩约 2027 年 5-6 月。
- **目标级别**：CCF-B，期刊优先，不冲 CCF-A。
- **算力**：实验室无 GPU 服务器 → 评估策略 = trace-driven 仿真（免费）+ 小硬件本地原型（免费）+ 关键大模型实验短期租云 GPU。
- **硬件**：Artix-7 XC7A35T（个人）、**XCVU13P（实验室新增，见增补）**、RK3588、Tofino P4 交换机、BlueField（按 BF-2 假设，需确认型号）。
- **能力基线**：vLLM monkey-patch + trace-driven 仿真；Verilog 手写 RISC-V CPU；KV Cache 管理一手经验。
- **预算**：租卡 1000 元内（极限 3000 元）。1×4090 市价约 1.5-2.5 元/小时，即约 400-600 小时，对 trace-driven 为主的研究足够。（增补更新：走 Mininet 纯软件或 FPGA 实测路线时主线可不租卡，租卡降为后期可选增强。）

## 选题 1：DPU 内联 KV Codec（首选）

**暂定英文标题**：*NICA: An Inline KV-Cache Codec on DPU for Disaggregated LLM Serving*（名称待定，避免与已有缩写撞车）

### 动机
PD（prefill/decode）分离架构中，prefill 节点每生成一批 KV 就要通过网卡传给 decode 节点。KV 传输量随上下文长度线性增长，是除显存外的第二大瓶颈，还引发 incast、占用 GPU 做压缩。已有系统的分工是：
- Mooncake [arXiv:2407.00079](https://arxiv.org/abs/2407.00079)、Blink [arXiv:2604.07609](https://arxiv.org/abs/2604.07609)、ShadowServe [arXiv:2509.16857](https://arxiv.org/abs/2509.16857) 把 SmartNIC 当**搬运 + 调度**；
- SpectrumKV [arXiv:2606.08635](https://arxiv.org/abs/2606.08635) 提出按 token 混精度（FP16/INT8/INT4）减传输，但只有软件/GPU timing；
- KIVI [arXiv:2402.02750](https://arxiv.org/abs/2402.02750) 的 2-bit KV 压缩在 GPU/CPU 上做。

**截至 2026-09，没有成熟工作把 per-block 的 KV 量化打包/反量化/布局重排做进 DPU 的内联数据面。** 这就是空白。

### 核心设计（3 个可独立成章的贡献）
1. **Inline codec pipeline on BlueField**：KV block 经 PCIe/RDMA 到达时，在 DPU 的 Arm 核 + 加速器上做流式压缩（建议先 INT8/INT4，对齐 KIVI 的非对称方案）与 gather 打包，对 GPU 呈现"零额外延迟"（压缩延迟被传输掩盖）。
2. **精度/布局感知的传输调度**：结合 SpectrumKV 思路，按 block 重要性（可用你已有的特征工程）动态选精度，网卡侧执行；用 credit/ACK 机制做反压。
3. **与 vLLM KV Offloading Connector 对接**：vLLM 已于 2026-01 发布官方 KV Offloading Connector（[官方博客](https://vllm.ai/blog/2026-01-08-kv-offloading-connector)），可作为天然集成点，降低侵入式改造成本。

### 评估方法（契合无 GPU 现状）
- **主体 trace-driven**：复用/扩展你的 vLLM trace，仿真压缩率、传输字节、pipeline 时序（不花钱）。
- **DPU 本地实测**：在 BlueField 上实测 codec 吞吐/延迟/CPU 占用（免费硬件）。
- **小规模真机闭环**：短期租 2 台带 GPU 的云主机（或 1 台多卡），跑 Qwen2.5-7B + ShareGPT，测端到端 TTFT、decode 吞吐、p99、压缩引起的精度损失（LongBench/PPL）。

### 目标场馆（2022 CCF-B，已核准）
- 期刊：**ACM TOS**（存储，专讲 KV offload 极对口）、**IEEE TCC**、**ACM TACO**。
- 会议：**ICCD**、**DATE**（硬件设计）。
- 注：TPDS 是 CCF-A，不作为目标。

### 8 个月里程碑
- 10-11 月：trace-driven codec 仿真器 + 复现 KIVI/SpectrumKV 基线。
- 12 月：BlueField 环境搭建（确认型号、装 DOCA），单 block codec kernel。
- 1-2 月：inline pipeline + vLLM connector 集成。
- 3 月：租云做真机实验，补齐数据。
- 4 月：写作投稿（期刊 rolling，时间压力小）。

### 风险与对策
- **BlueField 型号不明 / BF-2 算力弱**：BF-2 有 8×A72，INT8/INT4 流式整型算子够用；复杂 attention 绝不上 DPU。先花两周验证单 kernel 吞吐，不达标则降级为选题 2。
- **租双机较贵**：双机实验可压缩到 1-2 周集中跑，其余靠 trace 仿真。

## 选题 2：小 FPGA KV 协处理器（用上个人 FPGA）

**暂定标题**：*KV-Acc: An Off-Path FPGA KV-Cache Co-processor for Compacted Block Management in LLM Serving*

### 动机与必须正视的约束
XC7A35T 只有约 33,280 logic cells / 20,800 LUT / **90 个 DSP48E1** / 50×36Kb BRAM（≈225 KB）/ DDR3，算力约为 FlightLLM [arXiv:2401.03868](https://arxiv.org/abs/2401.03868) 所用 U280 的 **1/50~1/100**，**不能碰任何 GEMM**，也装不下完整 KV。因此定位必须是 **off-path（旁路）异步协处理器**，只做规则整型算子，绝不阻塞 GPU 主路径。

> **前提已变**：以上约束仅在"坚持使用个人 Artix-7 小板"时成立；实验室新增 **XCVU13P**（12,288 DSP、≈57 MB 片上、PCIe Gen3 x16）后，本选题应优先按增补第 3 节的 **选题 2+（VU13P on-chip KV 池加速器）** 推进。

### 与最接近工作的差异（防撞车）
- **CXL-SpecKV** [arXiv:2512.11920](https://arxiv.org/abs/2512.11920)（FPGA'26 Oral）：需要 **CXL 互连 + 数据中心 FPGA**，做推测预取 + 压缩。你的差异：**不用 CXL、用普通 PCIe/以太网旁路的最小器件**；聚焦 block 级"压缩 + 管理"而非推测执行。
- **HillInfer** [arXiv:2602.18750](https://arxiv.org/abs/2602.18750)：用 SmartSSD 做轻量 token importance 评估，是启发式。你的差异：**学习型 block 重要性预测**（直接接上你已做的 predictor）+ 独立小板。
- **PD-Swap** [arXiv:2512.11550](https://arxiv.org/abs/2512.11550)：靠 DPR 切换 prefill/decode，不做 block 管理。

### 核心模块（每个都是窄而深、35T 可综合）
1. **流式 KV codec**：INT4/INT8 ↔ FP16 打包/反量化（纯整型、规则、高吞吐）。
2. **block table + gather/scatter DMA**：管理物理 block 映射，辅助换页。
3. **学习型重要性排序器**：把你的 MLP predictor 精简为硬件友好的整数小网络（或 top-K/heavy-hitter 选择器），异步给驱逐/预取打分。
4. （可选）**RoPE / 在线 softmax 近似**单元。

### 评估
- FPGA 上给综合后资源占用、最高频率、codec/排序吞吐（latency/throughput）。
- trace-driven 评估接入后对命中率、换页量、TTFT 的影响。
- 短期租 1×4090 做端到端小规模验证。

### 目标场馆
- **FPGA**（CCF-B，FPGA 领域顶会，注意需比 FCCM/FPL 高一档）；**ICCD / DATE**。
- 期刊 **TACO / TOS**（均 CCF-B）。
- 注：FCCM/FPL/FPT 是 CCF-C，仅作保底。

### 风险与对策
- **35T 资源可能连一个模块都紧张**：先只做"codec + block table"两个最稳模块，学习型排序作为加分项。
- **板子与 GPU 主机连接**：达芬奇板带以太网/可走 PCIe？若互连麻烦，可做成"网络旁路 KV proxy"形态（FPGA 串在 GPU 与网络之间，呼应选题 1，但载体是 FPGA）。

## 选题 3：Tofino 辅助 KV-aware 路由 + INT 遥测驱动调度（最贴导师）

**暂定标题**：*KVRoute: KV-Cache-Aware Request Routing and INT-Driven Scheduling for Disaggregated LLM Serving*

### 动机
分离式 serving 中，请求该路由到哪个 decode 节点，取决于该节点已缓存哪些前缀 KV；但现有调度（Llumnix [arXiv:2406.03243](https://arxiv.org/abs/2406.03243) 的 KV 迁移、Mooncake 的全局池）要么在主机侧做决策、要么迁移本身有开销。**交换机位于所有 KV 流量的必经路径，天然掌握全局 KV 位置与链路负载，却没有被用于"KV-aware 路由 + 调度"**。

### 与实验室已有工作的差异化（关键！）
- **Monic**（INFOCOM 2026）：在数据平面上**算 MoE 模型**（compute offload）。
- **Quark**（INFOCOM 2025, best paper candidate）：在数据平面上**算 CNN**。
- **本选题**：交换机**不做模型计算**，只做 KV 的"路由定位 / 负载摘要 / 遥测反馈"，是 **networking assist**，与 Monic/Quark 的 compute offload 正交。可直接复用实验室 **SPRINT**（线速 INT 恢复）、**Carlo**（跨平面协作）、**dVRM/FlxVRM**（数据平面内存管理）的积累。
- **另需区分 Chimera** [arXiv:2602.12851](https://arxiv.org/abs/2602.12851)：它把线性化 attention 神经计算 + 符号约束映射到数据平面原语，用于**可信流量分析**；仍是"在数据平面算 attention"，本选题则不做任何模型/attention 计算，只做 KV 路由与遥测，定位不同。

### 核心设计
1. **线速 KV block 路由/定位协议**：在 Tofino SRAM 中维护紧凑的"前缀/block → 节点"摘要表（可能用 Bloom filter/sketch 压缩），交换机直接改写目的地址，提高 KV 命中率、减少迁移。
2. **INT 遥测驱动调度**：利用 SPRINT 的线速 INT，把各节点队列/KV 负载实时反馈给调度器，做不均衡感知的请求放置（呼应 BF 研究 [arXiv:2509.18114](https://arxiv.org/abs/2509.18114) 指出的 decode 负载不均问题）。
3. **资源约束下的表项管理**：Tofino SRAM/TCAM 有限、每阶段算术受限，表项压缩与老化是技术难点也是贡献点。

### 评估
- Tofino（bf-switch / 硬件交换机）上 P4 原型：线速、表项容量、路由命中率。
- trace-driven（ShareGPT/LMSYS 重放）评估命中率、迁移次数、p99 延迟。
- 对接 DistServe/Mooncake 开源栈做小规模仿真；真机 GPU 实验可少租。

### 目标场馆
- 期刊 **Computer Networks**（导师多篇 COMNET，B 类、熟门熟路）、**TNSM**（网络管理，B 类）。
- 会议 **CoNEXT / ICNP / IWQoS**（均 CCF-B）。

### 风险与对策
- **Tofino 表项装不下全局 KV 索引**：用 sketch/分片只存热点前缀，冷路径回退主机决策。
- **最依赖导师指导**：这是优点（实验室全套积累），但要尽早与崔老师确认选题不与其在投工作冲突。

## 选题 4：RK3588 NPU×KV 换页联合调度（边缘方向）

**暂定标题**：*EdgeKV: Joint NPU Offloading and KV Swapping for Long-Context LLM Inference on RK3588*

### 动机与已被证实的事实
- RK3588 内存带宽真实值：64-bit LPDDR4X 理论约 34GB/s，STREAM 实测 21-22GB/s（非"50-60GB/s"），decode 带宽墙即此。
- llm.npu（"Panda"，ASPLOS 2025，[arXiv:2407.05858](https://arxiv.org/abs/2407.05858)）证明 NPU 三限制：静态 shape、不支持 per-group MatMul、浮点弱；故"NPU 强 prefill、CPU 强 decode"。
- 端侧 KV 换页（KVSwap SenSys 2025、mzCache MobiCom 2026 [arXiv:2609.01338](https://arxiv.org/abs/2609.01338)、TierKV [arXiv:2609.21172](https://arxiv.org/abs/2609.21172)）是最新主线，**但都没有和 NPU offload 联合调度**。

### 核心设计
1. NPU 跑 prefill（其强项），decode 阶段 CPU 主导，把冷 KV 异步换出到 UFS。
2. **换页 × NPU 调度联合优化**：换页 I/O 与 NPU 计算流水线化，掩盖 I/O；按 block 重要性（可用你的预测思想）决定换出谁、预取谁。
3. 在 RKNN/RKLLM 限制（W8A8、静态图）下做最小侵入式集成。

### 评估（全免费硬件）
- RK3588 实测 Qwen2.5-1.5B/7B：t/s、首 token、长上下文最大长度、整机功耗（已知空载 4-5W、满载 10-12W）。
- 对比无换页 / KVSwap 式换页 / 本方案；精度用 LongBench。

### 目标场馆
- **SenSys / MobiSys**（CCF-B，边缘顶会，竞争激烈）；**Computer Networks**（B 类期刊，更稳）。
- 注：MobiQuitous、ICPADS 是 CCF-C，保底。

### 风险
- 端侧 KV 系统 2026 年集中爆发，撞车风险上升，需尽快锁定"换页×NPU 协同"这个具体交叉点。

## 选题 5：learned count 预测器驱动多动作调度器（纯软件，延续你的项目）

**暂定标题**：*OneLearner: A Single Reuse-Count Predictor for Joint Admission, Prefetch and Budget Allocation in LLM Serving*

### 撞车甄别（务必先读）
你的原项目（MLP 预测 block 剩余访问次数）在**核心新颖性上已被 KVLearn（ACM SYSTOR 2026, [DOI:10.1145/3793230.3837769](https://doi.org/10.1145/3793230.3837769)，代码 [github.com/FastLM/KVLearn](https://github.com/FastLM/KVLearn)）大幅覆盖**：其 Prefix Reuse Predictor 同样用结构/时序在线特征、不碰权重、block 粒度、对标 LRU，且有成本分 CARS + 在线阈值 + 真机 PD 分离。**不能在同点再投。**
其他 learned 工作（KVP [arXiv:2602.10238](https://arxiv.org/abs/2602.10238)、ForesightKV [arXiv:2602.03203](https://arxiv.org/abs/2602.03203)、NGC [arXiv:2604.18002](https://arxiv.org/abs/2604.18002)、KVpop [arXiv:2607.05061](https://arxiv.org/abs/2607.05061)）是 token/head 粒度、单请求内优化模型质量，与你非同点撞车。

### 增量空间（本选题立足点）
从"预测块会不会复用"升级为"**一个 count 预测器同时驱动多个系统动作**"：
1. 用剩余访问次数（比二值概率信息量更大）联合驱动 **admission（是否准入/缓存）+ 预取 + 在 running 请求间动态分配 KV 预算**——KVLearn 只做 keep/evict。
2. **在线冷启动学习**（免离线训练），衡量 workload 切换时的适应速度。
3. 目标从命中率换成 **TTFT / p99 / goodput**，并给驱逐风险界。

### 评估

## 2. 新增备选方向（非 KV/DPU 集群，2026-10 补）

> 上表的五个（+2 增补）选题全部属于 **KV / DPU / FPGA 集群**。以下是一个**独立的候选方向**，不占用租卡预算、不依赖实验室硬件，作为并行备选记录在此。

| 项 | 内容 |
|---|---|
| **方向** | **云游戏会话中断的"作废字节"与输入重放（Replay-on-Recovery）** |
| **一句话** | 中断时唯一有价值的是"输入→显示"的因果耦合；既然中断期间的帧在恢复时已全部过期，正确动作是**丢弃过期帧、重放缓冲输入、只交付一帧对账帧**，而不是把视频补回来 |
| **概念交叉** | rollback netcode（老，联网游戏 20 年）× 云游戏流式（帧有硬 deadline）× 移动性中断（Wi-Fi 漫游 / 4G-5G 切换 / 隧道） |
| **三视角审核结论** | ❌ **已证伪（2026-10-02）**。用户指出两处机制性缺陷：① 中断期间玩家会**乱点**，缓冲到的输入本身就是噪声，重放它反而新增"游戏做了玩家没想做的事"这一失败模式；② **游戏世界不会因玩家不动而停住**，重放等于把"基于过时信念的动作"施加到已演化的世界上。**rollback netcode 的类比对不上**——它的三个前提（回滚窗口仅几十毫秒、世界确定性、影响局部）在中断场景全部不成立。原"有条件成立"结论作废 |
| **命脉（go / no-go）** | **作废字节占比**。>5% 立项；2–5% 只能做二流论文；<2% 放弃或改造（对照本工作区 WTP-122 的"冗余被高估"教训） |
| **止损机制** | M0 只需 1–2 周，且**那个数字本身就是可发表的测量结果**，无论方向是否继续都不浪费 |
| **被否掉的首选** | "learning-augmented 帧调度 + 感知平台区做误差吸收"——已被 **Stein & Wei 2023**（deadline 包调度的 learning-augmented 框架）与 **MMSys'26 360° 视频学习增强码率分配**正面对撞，理由见文件 §7 |
