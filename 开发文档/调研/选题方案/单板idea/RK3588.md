## Idea 1：GateKeeper —— 家庭网关上"作废字节"一等目标 × 负载预测的峰值感知传输调度

- **暂定标题**：*Wasted-Byte-Aware Scheduling on a Home Gateway: Coupling Redundant-Transfer Suppression with WiFi Load Prediction*（中文：面向作废字节的家庭网关负载预测择时传输）

### 动机与研究空白
- WTP 专题的核心结论：ML 预测 WiFi 负载（WTP-1/2/3/4）、预测驱动削峰择时（WTP-18/20/22/23）、learning-augmented 保证（WTP-78/80/81）三块各自成熟，**真空白在第四块——把"无效/重复传输的字节量"作为一等优化目标并与负载预测耦合**：RE 文献（WTP-112~124）只做链路省带宽、不看负载时序；负载预测文献不涉及冗余抑制。
- **"中断 → 不可续传/粗粒度续传 → 已传字节作废 → 重传抬高高峰负载"这条因果链无任何量化研究**（12+ 组关键词、50+ 次查询零命中）。可类比的浪费口径都在视频侧：YouTube 冗余流量最高 33%（WTP-37）、短视频 45.2% 数据被浪费（WTP-39）、首个 wastage 严格建模（WTP-40）。
- peak-aware 竞争框架只在能源域被形式化（WTP-91/92/93），网络/带宽侧没有。
- **两份泼冷水证据必须先读**：WTP-122（真实无线流量冗余被高估）、WTP-123（接入链路瓶颈下缓存救不了）——它们决定本选题的"能省多少"可信区间。
- 技术前提修正（WTP §12）：HTTP Range 断点续传 1999 年已标准化（WTP-60），命题应是"减少已传字节的作废率"而非"发明续传"。

### 为什么 RK3588 是正确平台
- **它就是真实的家用网关硬件等级**：RK3568/RK3588 系是消费级路由器/软路由主流 SoC（OpenWrt 有官方支持），千兆/2.5G 双网口、空载 4-5W 可 7×24 常开——论文叙事是"部署在家庭网关上的系统"，x86 工控机反而失真。
- **NPU 让预测器"住在网关上"成为贡献点而非作秀**：负载预测模型（GBM/小 LSTM 量级）放在 6 TOPS NPU 上离线推理，与"云端预测"形成架构差异；同时可测预测推理本身的能耗（空载 4-5W/满载 10-12W 的功耗剖面现成）。
- 测量需要的被动流量观察、流量整形（tc/htb）、Per-flow 字节记账，Linux 网关形态全部原生支持。

### 实验设计（全部 RK3588 + 民用 PC + 家用 WiFi）
1. **M0 测量（决定生死，1-2 个月）**：RK3588 做网关，民用 PC/手机做客户端。构造三类作废场景：① 不可续传下载被打断重下（自建无 Range 的 HTTP 服务 + 公网真实大文件下载对照）；② 视频/预取类作废（复现 WTP-37/39 口径于家用 WiFi）；③ 高峰时段并发抢占导致的慢传输-放弃-重试。输出：**作废字节占总流量比例、作废对高峰 95 分位负载的抬升量**——这个数字本身就是可发表的测量结果（对标 Sieber/Zhang 的纯测量论文地位）。
2. **系统层**：网关侧实现"作废感知 + 负载预测"的择时调度——预测未来窗口负载（自采 trace 训练），对可延迟/可续传流量做准入与速率整形；基线：无调度 / 仅预测择时（复现 WTP-26 思想）/ 仅作废感知 / oracle。
3. **指标**：作废字节/session、高峰 95 分位链路利用率、传输完成时间、作废→高峰抬升的因果量。
4. **理论加分项（可选）**：把"压高峰作废字节"形式化为 peak-aware 在线问题，借 WTP-84（learning-augmented deadline 包调度）与 WTP-91（peak-aware 竞争框架）模板给最坏情况界——但论文主体是系统与测量，理论作为一节。

### 目标场馆
- 期刊 **Computer Networks（B）**：该刊收 WiFi 实测预测（WTP-4）与 DPDK 系统论文，导师组熟；**IEEE TCC（B）**可收调度+仿真类（KVT-36/37 证明纯仿真可进）。
- 会议 **CoNEXT / ICNP / PAM / IMC（均 B）**：测量部分天然适配 PAM/IMC。

### 主要风险与撞车检查
- **M0 数字可能很小**（重蹈 WTP-122 覆辙）→ 自带止损：M0 只需 1-2 个月，结果无论如何都是一条无人报过的测量结论。
- **撞车点**：WTP-26（UE 侧带置信度预测的择时释放）与 WTP-27（数字孪生预测拥塞提前改配置）最接近——差异化在①目标函数是作废字节而非吞吐/拥塞，②载体是家庭网关而非 UE/孪生平台，③测量先行。WTP-1/4 证明"负载预测本身"已无新意，绝不能把预测器当贡献。
- **与已有 idea 的区分**：Replay-on-Recovery 是云游戏会话内中断的输入重放（帧语义、流媒体栈）；本 idea 是通用弹性流量 + 网关 + 负载预测耦合，问题与机制都不同。

### 新颖性把握
- 测量部分（作废字节因果链量化）：**高**（多路独立检索一致空白；但受限流影响，立题前补检索）。
- 系统部分（作废×预测耦合调度）：**中**（空白 G1 证据强，但 WTP-26/27 在近邻，需把"一等目标"的差异写硬）。

## Idea 2：CloudDesk-on-RK3588 —— 云电脑（DaaS）的首个公开学术实测：瘦客户机视角

- **暂定标题**：*A First Academic Measurement Study of Cloud Desktops from a Real Thin Client*（中文：基于 RK3588 瘦客户机的云电脑端到端实测）

### 动机与研究空白
- 工作区最硬的空白之一（云游戏调研 §4 空白 2）：**云电脑无任何公开学术实测**——Azure Virtual Desktop / Amazon WorkSpaces / Windows 365 经 OpenAlex 逐项查证命中为零；协议级测量停在 2019–2021（唯一横评 CGB-2，2019 经典）。2026-10-02 补充检索验证：公开材料只有厂商对比报告与博客（LoginVSI EUX 等），仍无学术论文。
- 方法学模板现成：GeForce NOW 的 ISP 侧识别与实测（CGA-3，PAM'24）与运营商侧大规模扩展（CGA-4，ToN'26）证明"把这套测量方法搬到云电脑本身就是一篇论文"（调研原话）。
- 已有线索提示有东西可挖：生产 RDS 日志证明 **RTT 的时间波动（而非均值）与用户活动显著相关**（CGB-1）；云桌面吞吐预测已有冷启动/遗忘问题（CGB-3/4）但全无内容类型感知；桌面画面约 80% 图形数据是文字（CGG-3，工业文档口径）而现行质量指标对文字不可靠（CGE-7）。

### 为什么 RK3588 是正确平台
- **它是瘦客户机的真实硬件形态**（市面云终端大量采用 RK3568/RK3588 系 SoC），用它做客户端测出来的"端侧解码延迟、帧率、功耗"就是该品类的真实数字，x86 PC 反而没有代表性。
- 千兆/2.5G 有线 + 家用 WiFi 双接入，可分别刻画"有线 vs 家用 WiFi"下云电脑行为的差异；4-5W 常开便于做**数周级长期被动测量**（功耗成本可忽略）。
- 客户端完全可控：可插桩解码管线、记录逐帧到达/解码/显示时间戳，补 CGB-1 那种服务端日志拿不到的端侧视角。

### 实验设计
1. **可及性核对（第 0 步）**：确认能合法开通 AVD/Windows 365/WorkSpaces 试用或按量实例（月租约 $30-70 量级，预算内）；审阅 ToS 中测量条款。
2. **受控实验**：RK3588 客户端 × 三种负载（文档办公/网页滚动/视频），注入受控网络剖面（tc/netem：带宽阶梯、RTT 抖动、丢包），记录端到端延迟分解、码率自适应行为、**文字可读性随带宽的退化曲线**（接 CGE-7 的指标批判与 CGH-6/8 的屏幕内容质量评估方法）。
3. **野生测量**：数周长期运行，采集会话级流量特征，复现 CGA-3 的"仅从流量识别会话状态/活动类型"方法于云桌面协议（RDP/Blast/PCoIP-over-xxx）。
4. **产出锚点**：① 首份三平台公开数据集；② "波动 vs 均值"的端侧验证（呼应/挑战 CGB-1）；③ 文字退化曲线（直接给 TRACE 类编码研究当动机数据，但不与之撞车——本文只测不改）。

### 目标场馆
- 会议 **PAM / IMC（均 B）**——CGA-3 就是 PAM'24；期刊 **Computer Networks（B）**（CGA-6 同刊）。

### 主要风险与撞车检查
- **纯测量论文需要"发现"而非"数据"**：若结果只是"延迟还行、带宽自适应正常"，则平庸。对冲：把文字可读性退化与"波动伤害用户"两个预设发现点写进设计。
- **无服务端 ground truth**：只能黑盒；CGA-3/4 证明黑盒测量可发 B 类，但实验设计必须更精细（受控变量 + 统计检验）。
- **撞车风险低但非零**：CGB-3/4 作者组（Zuodong Jin 等）在做云桌面预测，若他们补一篇实测则正面相撞——立题前精读其最新工作。
- **成本与账号**：三平台订阅费数百元/月量级；需确认教育优惠或试用额度。

### 新颖性把握
- **高**（工作区逐项查证 + 本次补充检索双重支持"零学术实测"）；但"高新颖性 ≠ 高影响力"，影响力取决于发现质量，故风险列如上。

## Idea 3：NPUscope —— RK3588/RKNN 端侧 LLM 推理的首个学术刻画 + 能耗感知后端切换系统

- **暂定标题**：*Characterizing and Orchestrating NPU-CPU LLM Inference on a Commodity Edge SoC: An RK3588 Study*（中文：RK3588 NPU 推理刻画与能耗感知的 prefill/decode 后端动态切换）

### 动机与研究空白
- **测量侧空白**：移动 NPU 的 LLM 刻画已有 E12（"Is Your NPU Ready for LLMs?"，五框架×三后端，结论"NPU 强 prefill、CPU 强 decode"，最佳配置省能 54.8%）与 E17（Hydra，三代 Jetson × 13 LLM，10 万条记录开源），**但都未覆盖 Rockchip/RKNN**——2026-10-02 补充检索确认 RK3588 NPU 只有爱好者 benchmark 与厂商表（RKLLM benchmark.md、Turing Pi 实测），**无学术刻画**。RK3588 是国内边缘部署量最大的 SoC 之一，这个缺口是实打实的。
- **系统侧空白**：边缘端侧 LLM 调研 §4 空白 9 明确指出——"NPU 强 prefill、CPU 强 decode"已是测量结论，**但没有运行时按温度/频率/请求长度自动切后端的系统**。RK3588 的特殊性使这个问题非平凡：RKLLM 仅支持 W8A8（E 节路线 F）、静态图转换成本高（E1 量化的三大 NPU 限制）、big.LITTLE 4×A76+4×A55 不对称调度与 ~80℃ 降频点（Turing Pi 实测）都是切换策略必须考虑的变量。
- 方法论先例：E12/E17 的刻画口径可直接照抄并扩展（它们都没测能耗-温度-降频耦合，而 RK3588 被动散热板这个耦合很强）。

### 为什么 RK3588 是正确平台
- 这就是研究对象本身，无需论证；**换一块板就没有这个论文**（高通/联发科 NPU 已被 E12 覆盖，Jetson 已被 E17 覆盖）。
- 工具链现状（RKLLM 仅 W8A8、`.rkllm` 静态图、x86 离线转换）本身就是可刻画的"部署摩擦"维度，是 E12/E17 没有的贡献点。

### 实验设计
1. **刻画层（1.5-2 个月）**：Qwen2.5-0.5B/1.5B/7B × CPU(llama.cpp 各量化档) × GPU(Mali-G610) × NPU(RKLLM W8A8) 全组合，测 TTFT/t/s/峰值内存/功耗/温度曲线；重点刻画：① prefill-decode 的后端优势反转点（随 prompt 长度）；② 温度-降频-吞吐的长时耦合（25 分钟持续负载复现 Turing Pi 方法）；③ NPU 静态图转换成本与 batch/seqlen 敏感面。数据集开源。
2. **系统层（2-3 个月）**：在线 profiling + 切换控制器——按请求长度、当前温度/频率、队列深度在"NPU prefill+CPU decode / 全 CPU / 全 NPU"间逐请求选择，目标对齐 E12 的省能口径（≥30%）且不损 TTFT SLO。基线：固定后端 ×3、E12 式离线最优查表。
3. **评估**：全部本地、零成本；trace 用 ShareGPT/自采长度分布重放。

### 目标场馆
- 会议 **SenSys / MobiSys（B）**（E8 KVSwap 即 SenSys'25；竞争激烈需系统层足够硬）；IISWC 类workload刻画 venue（非 CCF，作副产）。
- 期刊 **Computer Networks（B）/ IEEE TCC（B）**保底；若系统层弱化为纯刻画，投 Computer Networks 的测量型论文。

### 主要风险与撞车检查
- **端侧 LLM 系统 2026 年集中爆发，撞车率全场最高**：PELM（K2026-33，端侧推测解码能耗优化，**待精读**）与 E12/E17 作者组的续作是最近威胁；每月复查 arXiv cs.AR/cs.DC 新稿。
- **RKNN/RKLLM 闭源工具链**：无法改 NPU 内部，贡献只能到"刻画 + 调度"层，审稿人可能嫌深度不足——用温度/降频/能耗这组别人没测的维度补深度。
- **非 KV 约束下的工作量天花板**：不碰 KV 管理时，系统层只有"后端切换"一个旋钮，需确认工作量够一篇 B；备选扩展是把切换推广到多任务并发（呼应 E9 mzCache 的多任务内存压力，但那是 KV 方向，只借场景不借内容）。

### 新颖性把握
- 刻画部分：**高**（双源验证无学术刻画；且 RK3588 装机量大，引用潜力好）。
- 系统部分：**中**（空白明确写在调研里，但"按状态切后端"思想简单，可能被 E12 续作顺手做掉）。

## Idea 4：EdgeDraft-NPU —— RK3588 NPU 起草 + 云端验证的通信高效协同推理

- **暂定标题**：*Speculative Decoding with an NPU-Bound Drafter: Edge-Cloud LLM Inference over Real WANs*（中文：NPU 静态图起草的边缘-云推测解码与 WAN 自适应）

### 动机与研究空白
- SpecEdge（E15，NeurIPS'25）证明"边缘起草、云端验证、只传 token"的可行性：服务器吞吐 2.22×、成本效率 1.91×，且实测层切分比纯云端慢 2.35×（否决了 Neurosurgeon 式路线）。**但其边缘侧是消费级 GPU**——6 TOPS、W8A8、静态图的 NPU 起草端没人做。
- 空白（边缘端侧 LLM 调研 §4 空白 5）：draft 模型恰好是**短、定长、规则**的计算——是 NPU 静态图限制下少数天然适配的负载；而"随真实 WAN RTT 自适应 draft 深度"在 E15 里也没有。CE-CoLLM（E14）证明上下文传输是云边协同主瓶颈，推测解码"只传 token"正是其解法。
- 与 KV 方向的安全距离：本 idea 传的是 token 不是 KV，不做任何 KV 放置/驱逐/压缩，与选题 4/四板卡组合无重叠。

### 为什么 RK3588 是正确平台
- **draft 负载与 NPU 限制完美咬合**：定长小模型、静态图、INT8——llm.npu（E1）量化的三大 NPU 限制（静态 shape、无 per-group、弱浮点）对 draft 前向几乎不咬人。
- 能耗是差异化指标：4-5W 常开的起草端 vs SpecEdge 的桌面 GPU，"每接受 token 能耗"是云端方案给不出的故事（同四板卡组合 §3 的能耗差异化逻辑）。
- 2.5G/千兆网口 + 家用 WiFi 恰好是"真实 WAN/边缘接入"的实验条件，不需要仿真网络。

### 实验设计
1. RK3588 跑 0.5B/1.5B draft（RKLLM W8A8 NPU vs llama.cpp CPU 双路径）；云端用民用 PC + 租按量 API（或本地 PC 跑 7B/14B GGUF 作"弱云"）做验证端。
2. 自适应控制器：按实测 RTT/抖动调 draft 长度（接受率-投机深度权衡），基线：固定深度、SpecEdge 式 GPU 起草（用 PC GPU 模拟）、纯云端。
3. 指标：端到端 token 延迟、接受率、通信字节/query、**每 token 能耗（端侧功率计/INA 传感器）**。
4. 网络条件：真实家用 WiFi + 公网 API，加 tc/netem 扫 RTT 14-100 ms。

### 目标场馆
- 期刊 **IEEE TCC / Computer Networks（B）**；会议 **CoNEXT / ICNP（B）**；若端侧系统味做足可试 SenSys。

## Idea 5：LittlePoll —— big.LITTLE 感知的内核旁路包处理能耗调度

- **暂定标题**：*Energy-Proportional Kernel-Bypass Packet Processing on Asymmetric Multicore*（中文：RK3588 大小核上的 DPDK/XDP 能耗-性能联合调度实测与机制）

### 动机与研究空白
- 内核旁路的代价侧研究正在升温：Metronome（DBK-27）证明 busy-polling 独占核的代价并做自适应间歇取包；EnergyTracer（DBK-33）做 DPDK 事件级能耗归因并指出轮询模型是能耗软肋；DBK-25 划清了边缘数据中心里旁路的适用边界；DBK-16 是"旁路非银弹"的反方必读。
- **未见的组合**：所有上述工作都在 x86 对称多核上。**big.LITTLE（4×A76+4×A55）上的内核旁路没人刻画过**——轮询线程放大核（快但费电）还是小核（省电但可能追不上线速）？DVFS 与轮询/中断混合模式（Metronome 思路）在大小核间如何分配？sched_ext（DRE-8，主线 6.12+）第一次让"用 eBPF 写 CPU 调度策略"可落地，恰好可以做这个调度器而不改内核。
- 注意与选题 A 的区分：选题 A 是 DPDK 用户态 **KV 传输**数据面；本 idea 是**通用包处理的能耗调度**，不碰 KV 语义。

### 为什么 RK3588 是正确平台
- 它是**最容易到手的 big.LITTLE + 完整 Linux 主线支持 + 可测功耗**的平台；x86 上不存在大小核问题，服务器 ARM（如 Graviton）是对称核。
- 2.5GbE 的线速（约 370 kpps@64B… 实测小包压力中等）恰好落在"小核可能追不上、大核绰绰有余"的敏感区间——这个"临界带宽"反而制造了真实的调度权衡空间。

### 实验设计
1. **刻画**：DPDK testpmd/自研转发 × XDP 对照，扫 64B-1500B 包长 × 大核/小核/混部 × DVFS 档位，测 pps、p99 延迟、每包焦耳；给出"大小核反转点"曲线。
2. **机制**：sched_ext 写能耗感知调度器（轮询线程按负载在大/小核间迁移 + Metronome 式睡眠深度自适应），基线：钉大核、钉小核、内核默认 EAS、Metronome 复现。
3. 对照：民用 x86 PC 跑同实验，证明现象是大小核特有。
4. 负载：L2/L3 转发 + 一个轻量 NF（如基于 XDP 的 Katran 式负载均衡，DRE-4）增加现实性。

### 目标场馆
- 会议 **CoNEXT / ICNP（B）**（XDP 原始论文 DBK-20 即 CoNEXT'18）；期刊 **Computer Networks（B）**。

### 主要风险与撞车检查
- **动机强度存疑**：2.5GbE 对 8 核 RK3588 可能根本吃不饱和——若大核单核即线速，"调度权衡"坍缩成"永远钉大核 + 关小核"，论文变薄。**第 0 步必须先测这个饱和点**（1 周内可出结果，自带止损）。
- Metronome/EnergyTracer 占位"能耗×轮询"，本 idea 独占的只剩"大小核不对称"一个维度——新颖性系于该维度是否产生非平凡现象。
- DPDK 在 RK3588 的 PMD 支持（通常走 vfio/uio + 标准 e1000/igc 或虚拟口）需先趟通；2.5G 瑞昱网口的 PMD 兼容性待验证。

### 新颖性把握
- **中低**（组合未检索到先例，但单点都有近邻；且存在动机坍缩风险，先测饱和点再决定投入）。
