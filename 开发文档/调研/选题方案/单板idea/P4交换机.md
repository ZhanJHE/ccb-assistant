# P4 可编程交换机单板研究 idea 集（非 KV-cache 方向）

> 创建：2026-10-02。为研究生（8 个月窗口 2026-09→2027-05，目标 CCF-B，期刊优先 Computer Networks / IEEE TCC / JPDC，会议 CoNEXT / ICNP / IWQoS / IMC）构思的 P4 数据平面可编程交换机研究 idea。
> **硬件假设**：实验室已有 Tofino 设备可用（注意 NPD-17：Tofino 已于 2024-08 停产、open-p4studio 的 BSP/驱动申请窗口 2026-01-01 起关闭——**新增环境不可行，但存量设备继续使用不受影响**）；若 Tofino 环境不可用则退到 **bmv2 + Mininet** 软仿（该路线已被导师组 CCF-B 论文的方法学间接支持），软仿时用 p4c/p4studio 编译器报告资源占用以佐证真机可行性。
> **排除（占位边界）**：
> - KV-cache / LLM serving 数据面（已由**选题3 KVRoute** 占位：Tofino 辅助 KV-aware 路由 + INT 驱动调度）；
> - "在数据平面跑 ML 模型推理"（Monic=MoE、Quark=CNN、IIsy NIAC2026-6、Planter NIAC2026-7 已占位）；
> - 云游戏中断的"输入重放"恢复（2026-10-02 已证伪，见《云游戏-中断恢复与作废字节-idea与三视角审核.md》，机制前提不成立，勿复活）；
> - 通用 LLM 推理系统（无 GPU 服务器）。
> **依据**：全部空白判断挂 `文献索引.md` 真实编号（WTP / CGA-CGE / NIAC2026 / NPD / DRE 节）与对应主题综述；本轮仅做 3 次轻量验证性搜索（见 §7），未新增文献登记。
> **定位**：全部 5 个 idea 均为 **networking assist / 数据面服务**——交换机不做模型计算（与 Monic/Quark 正交），只做匹配、计量、调度、目录；预测/模型一律放控制面或端侧。

## P4-RE｜DedupGate：预测门控的可编程数据面流量冗余消除

**暂定标题**：*DedupGate: Load-Prediction-Gated Traffic Redundancy Elimination on Programmable Data Planes*

### 动机与研究空白
- **TRE-PRO（WTP-124，IEEE Network 2021）是可编程数据面上做通用流量冗余消除（TRE）的唯一直接实现，S2/OpenAlex 引用均为 0**，2021 年后该子方向无一篇跟进；同期"在网去重"全部转向应用侧（CableCache 请求级去重 NPD-1/WTP-132；MPINT 遥测去重 WTP-133）——这是工作区调研明确标注的 **"能力涨、人没做"缺口**（WiFi 调研 §6.5 与空白 G6）。
- RE 本身有 25 年积累与权威区间（Spring & Wetherall 开山 WTP-112；SmartRE WTP-113；EndRE 企业链路平均省 26% WTP-115；COMST'14 综述：接入链路 15–60%、Wi-Fi 近 50% WTP-116），但 **RE 文献只做链路省带宽、从不看负载时序**；WiFi 调研的**真空白 G1** 正是"把无效/重复传输字节量当一等优化目标并与负载预测耦合"（§10，证据强度强）。
- 负载预测侧已是成熟红海（WTP-1~4：企业 WiFi AP 负载预测平均误差 <20%、100 AP×3 个月实测），**可直接当输入用，不需要再发明预测器**。
- 场景更新（2026 年的冗余在哪）：容器镜像/软件分发的重复拉取有实测痛点（Seekable OCI WTP-57、DBPP 分块拉取撑爆内存 WTP-58）、URI 别名与资源修改导致重复传输（WTP-129）、视频多码率并行下载冗余最高 33%（WTP-37）。DC 内部与企业出口存在大量明文/协议可知的高冗余流，绕开 TLS 不可见问题。
- **一句话命题**：冗余消除的收益是带宽、代价是交换机 SRAM 与算力——**平时关掉、预测到高峰才开**。把"何时值得做去重"本身作为研究对象，是 RE 文献 25 年没人问过的问题。

### 为什么必须在交换机数据平面
1. 去重必须在**字节经过的位置**做：端主机只做得到自己一份（EndRE 已证明端侧可行但覆盖单点），跨租户/跨流的冗余只有汇聚点（ToR/出口）看得见；DPU 只覆盖单主机，控制器太慢且无法线速处理每包。
2. 去重需要**线速逐包指纹 + 大容量指纹缓存**——这正是交换 ASIC 相对通用 CPU 的结构性优势（NetCache 已在 Tofino 上演示 64K×16B 键表 + 8MB 值表，NIAC2026-4 补充数字）。
3. "门控"决策（开/关去重）要作用于**每个包**，控制面逐流干预不现实；预测只在控制面周期下发阈值，数据面自维持。

### P4 可行性分析
- **指纹计算**：经典 Rabin rolling hash 含乘法与滑窗，Tofino 每级 ALU 只支持有限算术 → 改用硬件 hash unit（CRC 族）对**固定采样点**或**固定块边界**取指纹，牺牲 CDC 的边界对齐精度换线速——"hardware-friendly fingerprinting 的设计空间"本身是论文贡献点。跨包滑窗状态可用 register 保存上一包尾部若干字节的哈希种子（有状态操作，1 次/包，无需 recirculation）；若要做块内多指纹，用 packet recirculation 多趟处理（OrbitCache NPD-2 已用 recirculation 处理变长 item，有先例）。
- **指纹缓存**：SRAM register 哈希表存 `指纹 → 存在位/引用ID`，64K~1M 条量级在 Tofino 上可行（对照 NetCache 64K 条只用部分 SRAM）；冲突即保守判"不重复"（只损失收益不产生错误）。
- **替换与还原**：命中后将重复段替换为 shim 头（引用 ID + 长度），需**配对交换机/端代理还原**——与 TRE-PRO 的 switch-to-switch 形态一致；未命中直传。shim 改写涉及包长变化，Tofino 的 deparser 支持，但 payload 截断/回填要占用额外 stage，预计需要 recirculation 1 次 → 吞吐折半以内的代价，需如实报告。
- **TCAM**：仅用于流分类/门控规则（少量表项），压力小。
- **阶段预算粗估**：解析+分类 2~3 stage、指纹 2~3、查缓存 2、改写/还原 3~4，单趟 12 stage 内可收，超了走 recirculation——这些不确定性本身是论文的 feasibility 一节。

### 实验设计
- **平台**：Tofino 真机两台配对（发送侧去重 + 接收侧还原）或单机 loopback 口配对；**bmv2+Mininet 保底**（注意 bmv2 无真 hash/stage 限制，须用 p4c 编译报告佐证资源，且只报告功能正确性不报性能）。
- **流量**：① 公开企业/DC trace 重放（EndRE 口径，WTP-115）；② 自采高冗余场景：容器镜像仓库拉取 storm（对照 WTP-57/58 的镜像分发痛点）、软件更新分发、备份流；③ 反方场景也必须测：加密比例高/内容去同步的流量（正面回应 WTP-122）。
- **预测门控**：用现成 AP/链路负载预测器（WTP-1/4 的方法或直接合成预测序列）驱动去重开/关/降级三档；对照组：常开、常关、oracle。
- **基线**：TRE-PRO 按论文复现（无开源）、端主机 RE（EndRE 式）、纯压缩（gzip 旁路）。指标：省字节率、高峰时段链路峰值利用率、无效传输字节占比、交换机资源占用、每包额外延迟。

### 目标场馆
首选 **CoNEXT / ICNP（B）**，期刊扩展投 **Computer Networks（B）**；测量占比重时可试 **IMC（B）**。PAM（B）亦可作测量向出口。

### 风险与撞车检查
- **撞车**：低。TRE-PRO 引用 0 且本轮验证搜索（tavily，2026-10-02）未见 2021 后同方向实现；应用侧去重（NPD-1 CableCache、WTP-133 MPINT）去重对象与目标均不同，属可引用的邻居而非撞车。
- **风险 1（动机反方）**：WTP-122 实测真实无线冗余远低于文献值、加密进一步削弱——必须选题定位在高冗余可知场景（镜像分发/备份/企业明文段），并把 WTP-122/123 写进 related work 正面回应，不夸大节省区间。
- **风险 2（真机可行性）**：payload 深度解析 + 改包长可能超 stage/recirculation 预算——裁剪路线：先做 packet-block 级去重（整包/半包粒度）证明框架，CDC 级作为扩展；bmv2 路线下以功能+资源估算为主。
- **风险 3（还原端部署）**：配对设备假设在真实网络未必成立——实验内限定"DC 内 ToR 对/企业出口对"并明确部署前提。
- **新颖性把握：高**。依据：WTP-124 引用 0、WiFi 调研 G6 结论、本轮搜索无跟进。

## P4-QoS｜FrameGate：帧语义 × 硬 deadline 的云游戏数据平面调度

**暂定标题**：*FrameGate: Frame-Semantic, Deadline-Aware Scheduling for Cloud Gaming Traffic in the Data Plane*

### 动机与研究空白
- 云游戏是**与视频直播需求结构不同**的负载：最低 10–20 Mbps（CGA-3，比本地主机游戏高 2 个数量级）、60–120 fps、交互回路硬 deadline（网络良好时端到端仍 112–403 ms，CGA-1）、存在感知最大帧率 pFR（CGA-7，超过即浪费）。Wi-Fi 接入长尾由 AP 竞争主导（CGC-5 BLADE）。
- **真空白 5（云游戏调研 §4）**：learning-augmented × 硬 deadline 的交互式视频传输——RTC 拥塞控制 12 条检索无一相关，而该方法论在交换机调度（WTP-84/85）、360° 视频（WTP-89）、能源 peak-aware（WTP-91）均有落地。
- **真空白 4**：传输层缺"媒体重要性"统一抽象——MoMQ 诊断出多路径调度器"只看到字节、看不到关键帧"（CGC-12），各家自造重要性表达互不兼容。Camel（CGC-3）进一步证明**包级 CC 被编码的帧级时变误导**，需要帧级观测。
- 最近的邻居是 **Scallop（CGC-18，SIGCOMM'25）**：把视频会议 SFU 拆成硬件数据面+软件控制面。差异化清晰：①对象是**高码率游戏流（10–20 Mbps × 60–120 fps）而非会议（0.5–5 Mbps）**；②我们不做中继/SFU，做**瓶颈点的跨流帧级调度**；③我们带 deadline 语义与学习增强保证，Scallop 没有。
- D3 的"晚到 = 无用"（WTP-69）给出理论许可：**注定过期的帧，主动丢弃优于排队**——丢在交换机还能省下游字节（与"作废字节"命题挂钩，WTP 调研 §12）。

### 为什么必须在交换机数据平面
1. 帧级调度只能发生在**排队点**；端主机看不到瓶颈队列深度与其他流，AP/上行的缓冲区在交换机侧。云游戏的瓶颈常在接入汇聚（CGC-5），端侧 CC 只能间接感知。
2. 交换机**同时看到所有用户的流**：能在多条游戏流共享瓶颈时做跨流仲裁（保每条流的 I 帧与可达帧、丢注定过期的 P 帧），这是任何单端方案结构性做不到的。
3. DPU/端侧能做发送整形但管不了对端方向与共享瓶颈；控制器环路是毫秒级，帧 budget 是 8–16 ms 级。

### P4 可行性分析
- **帧语义解析**：RTP/UDP 载荷的 H.264/265 NAL header、RTP marker bit、时间戳均在固定浅偏移，P4 parser 直接可达；QUIC/加密场景退化为"包大小簇 + 到达间隔"的帧边界推断（Camel 同口径，可在论文中两档都测）。
- **per-flow 状态**：register 存每流帧边界、帧大小累计、deadline 时钟；数千并发流在 SRAM 预算内（每流几十字节）。
- **调度**：Tofino 每端口硬件队列数量有限（典型 8~32），EDF 需近似——优先级分层 + **入队时 deadline-aware push-out/drop**（注定过期包直接丢或顶出低价值包）；时间戳比较是简单算术，单趟可完成，无需 recirculation。严格 EDF 的近似误差是论文分析点。
- **学习增强部分**：预测（未来带宽/帧到达）由控制面周期下发为**表项/阈值**（不开、关、降三档调度策略 + 置信度档位），数据面只做查表与计数——**不在数据面跑模型**，与 Monic/Quark 划清界限；consistency/robustness 分析照 WTP-84 模板。

### 实验设计
- **平台**：Tofino 做瓶颈（rate-limit 到 10–100 Mbps 模拟最后一跳/上行），多台民用 PC 跑真实云游戏推流（ffmpeg/WebRTC 推录制好的游戏画面，无需 GPU）；**bmv2+Mininet 保底**（bmv2 队列简单，需用 simple_switch 优先级队列或自定义 egress 逻辑近似，论文注明保真度边界）。
- **网络条件**：公开蜂窝/Wi-Fi 吞吐 trace 重放（Lumos5G WTP-66 口径；BLADE 的 Wi-Fi 竞争场景用 netem + 模拟 AP 竞争流注入）。
- **基线**：FIFO、FQ/优先级、D3 式纯 deadline、Scallop 数据面思路的裁剪复现、端侧 Pudica（CGA-13）对照。指标：**帧级 deadline miss 率、可解码帧占比、作废字节量、p95/p99 帧延迟、预测注入误差下的退化曲线（robustness 证据图——别人都没有的一张图）**。

### 目标场馆
首选 **IWQoS（B，QoS 语境正合）/ CoNEXT（B）**，期刊扩展 **Computer Networks（B）**；若理论分析做扎实可试 ICNP。

### 风险与撞车检查
- **撞车**：中低。Scallop（CGC-18）是最近邻居，差异化如上；5G UPF 的 P4 QoS（本轮搜索仅见切片级 QoS 框架与 ABR 演示，非帧语义×deadline）不构成撞车。MMSys 社区有 video-aware networking 历史工作，立题前需补一轮该社区检索（未做，受限流约束）。
- **风险 1**：加密 QUIC 下帧语义不可见 → 双档设计（RTP 可见档 + 推断档），推断档单独报告精度损失。
- **风险 2**：体验指标主观——用 pFR/可解码帧率等客观代理（CGA-7/9 口径），不做用户实验。
- **风险 3**：与导师组 SPRINT 的关系——本 idea 若用 INT 做帧级反馈，只是**消费**遥测；贡献在调度语义，需在论文中写清。
- **新颖性把握：中高**。依据：云游戏调研空白 4/5（多处独立检索一致）+ WTP-84/89 方法论移植空位；扣分项是 video-aware scheduling 的历史文献尚未穷尽检索。

## P4-TEL｜WasteScope：作废字节的交换机线速计量与事件去重遥测

**暂定标题**：*WasteScope: Line-Rate Accounting of Wasted Bytes and Deduplicated Telemetry in Programmable Switches*

### 动机与研究空白
- WiFi 调研**真空白 G2**："中断 → 无续传 → 从零重下 → 抬高高峰负载"这条因果链**无任何量化研究**（12+ 组关键词、50+ 次查询零命中）；调研同时给出升级口径——"减少已传字节的作废率"（§12），可对接现成的浪费占比数字（YouTube 冗余最高 33% WTP-37、短视频 45.2% WTP-39、严格建模 BDV WTP-40）。
- 遥测侧的成本问题已被部分回答：**MPINT（WTP-133，CoNEXT'25 workshop）用交换机内去重把 INT 开销降 >80%**——但它只做"多路径 INT 去重"这一件事，且是 workshop 短文；"把遥测上报本身按状态去重（变化才报）"作为通用机制尚无人系统化。
- 半占位：NTP-INT（WTP-17）用流量预测剪枝 INT 探针路径，目标是控开销，不测"作废"；导师组 SPRINT 是 INT 恢复机制本体。**本 idea 的贡献在"作废"这一测量语义 + 事件去重遥测的通用化**，与两者边界清晰。
- **一句话命题**：把"wasted bytes（已传但作废的字节）"提升为网络遥测的**一等指标**——现在没有任何遥测体系报告它，而它恰恰是高峰负载的一部分成因。

### 为什么必须在交换机数据平面
1. 只有网络中间点能**同时看到"已传"与"重传"两遍字节**（端主机只见自己一次；控制器粒度太粗）；作废的判定需要跨时间窗比对同对象流量，正是有状态数据面的位置。
2. 线速 per-flow 计数 + 对象指纹匹配是交换 ASIC 的强项；DPU 只见单主机，端主机无全网视图。
3. "变化才报"的事件去重必须在数据面完成（否则上报流量本身又成开销）。

### P4 可行性分析
- **作废检测（三档语义）**：① 中断重下：流中途 RST/超时后，同对象指纹（五元组 + 对象标识/初始字节哈希）再次出现且前次未传完 → 记前次已传字节为作废；② 多码率重复：同对象不同表示的重复取回（WTP-37 口径）；③ 过期投递：携带 deadline 语义的流（配合 P4-QoS 的标记）在过期后仍到达的字节。检测全部归约为 register 计数器 + 哈希表查重，**算术简单、单趟可成**。
- **容量**：per-flow/对象计数数万~十万条（Count-Min 兜底统计 Top 浪费对象）；精度-内存权衡是论文分析点。
- **事件去重遥测**：register 存上次上报值，变化超阈值才生成遥测包（INT 扩展头），把 MPINT 的"去重"从多路径场景推广到时间维度；上报通路可用 SPRINT 的 INT 管道（**复用不重造**）。
- bmv2 友好：测量逻辑不依赖 Tofino 特有 hash 单元，软仿保真度高——**这是 5 个 idea 里 bmv2 路线最稳的一个**。

### 实验设计
- **平台**：bmv2+Mininet 即可完成主体（功能与精度）；Tofino 真机补线速与资源数据。
- **流量**：① 受控浪费场景：容器镜像并发拉取 + 故障注入（netem 断链/AP 切换模拟，驱动"中断重下"）；② ABR 视频 trace 重放（WTP-37/38 口径）；③ 背景流量用公开 DC/校园 trace。
- **验证**：离线 ground truth（pcap 全量后处理）对比线速计量的误差；遥测开销（字节占比）对比全量 INT 与 MPINT 复现。
- **产出形态**：测量方法论 + 线速计量系统 + 一批"作废字节占比 × 负载时序"的首个数字（动机段自此有数可引）。

### 目标场馆
首选 **IMC（B，测量口径正合）/ CoNEXT（B）**；期刊 **Computer Networks（B）**。若实测数据够大（校园网部署），有冲 A 的潜力但不作承诺。

### 风险与撞车检查
- **撞车**：低。MPINT 是 workshop 短文且场景不同；NTP-INT 目标不同；视频浪费测量（WTP-37~43）全部在端侧/应用侧做，无人把它做成网络遥测指标。
- **风险 1**：测量论文吃数据规模——8 个月内争取在校园网/实验室 AP 做小规模真实部署补一组真实数据；做不到则以受控实验 + 公开 trace 为主，诚实标注外推边界。
- **风险 2**："对象指纹"在加密/动态内容下不稳定 → 限定协议可知场景（HTTP/容器 registry/ABR），与 P4-RE 共享场景边界。
- **风险 3**：与 SPRINT 的差异化必须写清（SPRINT=INT 管道；我们=计量语义+上报去重）。
- **新颖性把握：中高**。依据：WiFi 调研 G2（零命中，但受限流影响标"中"）+ 遥测语义空白（多源一致，标"高"），综合取中高。

## P4-SCH｜PeakGate：learning-augmented peak-aware 的交换机准入与包调度

**暂定标题**：*PeakGate: Learning-Augmented Peak-Aware Admission and Scheduling on Programmable Switches*

### 动机与研究空白
- WiFi 调研**空白 G3**：**peak-aware 只在能源域被形式化**（WTP-91 peak-aware 竞争框架、WTP-92 削峰+ML 建议+最坏界、WTP-93 风险敏感版），网络/带宽侧从未有人把"压峰值"写成竞争目标——这是该调研认定的"最干净的一个理论空白"。
- 方法论模板现成：learning-augmented 的 consistency/robustness 框架（WTP-78 奠基、WTP-80/81 综述）+ **交换机场景的落地模板**（WTP-84 带 deadline 的在线包调度、WTP-85 FIFO 缓冲管理 1-consistency/√3-robustness）+ deadline 语义（D3 WTP-69）+ 可延迟流量调度（WTP-18/74）+ 准入控制形式化（WTP-28）。
- 预测输入成熟（WTP-1~4），**预测器不是贡献**——贡献在"把预测接进交换机准入/调度并保最坏界"。
- **一句话命题**：瓶颈链路上 inelastic（带 deadline）与 deferrable（可推迟）流量混合到达，目标从"均吞吐/平均延迟"换成"**峰值链路负载**"，用负载预测做准入/推迟/降级决策，预测再烂也不差过纯在线基线一个常数因子。

### 为什么必须在交换机数据平面
1. 峰值发生在**队列**；准入与推迟必须在入队点以包粒度执行——端主机只能控制自己，控制器是毫秒级环路，而削峰决策窗口是队列排空时间级。
2. "推迟"的网络侧实现 = 把可延迟类流量放进**定时释放队列**，只有交换机有缓冲与队列结构来做；DPU 只能推迟本机流量。
3. 数据面只执行查表与计数（预测在控制面下发），符合 P4 能力模型，也与"不在数据面跑模型"的占位边界一致。

### P4 可行性分析
- **准入决策**：预测值（控制面写表）+ 当前队列占用（register）做阈值比较——简单算术，1~2 stage。
- **推迟机制**：calendar-queue 近似——按"释放时刻"映射到有限硬件队列 + 周期队列轮换（控制面定时器驱动队列使能）；严格时间轮不可行，近似误差进理论分析。
- **deadline-aware drop**：入队时比较 `当前时刻 + 队列等待估计` 与 deadline，过期即丢（D3 语义），算术简单。
- **状态**：每类流量 credit/计数 register，无 per-packet 复杂有状态操作，**无需 recirculation**——是 5 个 idea 里数据面最轻的一个，Tofino 可行性风险最低。

### 实验设计
- **理论（2.5 月）**：单瓶颈链路、两类流量模型，证 consistency/robustness 界（照 WTP-91 的 peak-aware 框架 + WTP-84 的网络场景模板迁移）；给出预测误差 ε 的函数化性能界（WTP-83 口径）。
- **系统（2.5 月）**：Tofino 实现准入+推迟+丢弃三机制；bmv2+Mininet 保底（队列近似的保真度需注明）。
- **流量**：潮汐模式真实 trace（校园 WLAN/DC，WTP-108 已证潮汐浪费直觉）；注入可控误差的预测序列做 robustness 扫描。
- **基线**：纯在线（无预测）、纯预测（无保证）、WTP-84 式 learning-augmented。指标：峰值链路利用率、峰值队列占用、deadline miss 率、deferrable 流量完成时间、**预测误差-性能退化曲线**。

### 目标场馆
首选 **ICNP / IWQoS（B，"理论+系统"形态均收）**；理论扎实后期刊投 **IEEE TCC（B）** 或 Computer Networks。SIGMETRICS（A）8 个月不现实。

### 风险与撞车检查
- **撞车**：低。WTP-84/85 是平均/竞争比目标非 peak-aware；WTP-91/92/93 在能源域；WTP-28 是准入但无学习增强无峰值目标。立题前仍需按 AGENTS.md 补一轮不受限流检索（WTP 调研已标注该局限）。
- **风险 1**：数学门槛——8 个月内"证明+系统+写作"紧张；裁剪：理论只覆盖单瓶颈+两流量类，多跳/多类放 future work。
- **风险 2**：峰值目标的工程意义可能被审稿人质疑（ISP 按 95 分位计费、DC 按容量规划是两个现成动机，需写好）。
- **风险 3**：calendar-queue 近似在硬件队列数受限时的失真——用 Tofino 真机数据说话，失真大则降级为"两档推迟"。
- **新颖性把握：中高**。依据：WiFi 调研 G3（"最干净的理论空白"，证据强度中强）+ 模板齐备（可迁移性高、首创性打折）。

## P4-DIR｜RelayDir：亚 RTT 在网目录用于 RTC 会话迁移与多路径协调

**暂定标题**：*RelayDir: Sub-RTT In-Network Directories for Interactive Media Session Mobility and Multipath Coordination*

### 动机与研究空白
- **范式地基**：Pegasus（NPD-3，OSDI'20）证明"交换机 = 在网一致性目录"可行（追踪对象副本位置并据此转发）；NetChain（NIAC2026-5，NSDI'18）证明数据面协调可达亚 RTT。**两者全部落在存储/KV/锁场景；本轮验证搜索（2026-10-02）确认该范式未迁移到媒体/RTC 类负载**。
- 需求侧：交互式媒体的**移动性与多路径**痛点被反复证实——Wi-Fi/蜂窝切换是云游戏长尾来源（CGC-5）、WiFi 切换成本是经典结论（WTP-52，引用 861）、多路径 RTC 调度器"看不到关键帧"（CGC-12 MoMQ）、MultiMoQ 承认 MoQ 带宽受限下鲁棒性不足（CGC-13）。迁移/换路窗口内的包错投与丢失就是"作废字节"的又一来源。
- **一句话命题**：会话在边缘节点间迁移、或流在多路径间切换时，位置/路径状态的传播是 RTT 级控制面操作——把这张"会话 → 位置/路径"目录放进交换机，把迁移窗口从"一个或多个 RTT"压到亚 RTT，窗口内双投兜底。
- **与已证伪 idea 的边界**：《云游戏-中断恢复与作废字节》的输入重放机制已被证伪（依赖"世界停住"假设）；本 idea **不做输入重放、不碰游戏状态**，只做网络层位置目录与转发，不依赖任何被证伪的前提。

### 为什么必须在交换机数据平面
1. 迁移窗口是 RTT 级事件，控制器下发流表是毫秒~秒级——NetChain 的整套动机（协调从多 RTT 压到亚 RTT）原样适用。
2. 目录查询必须在转发路径上（每包一次"去哪"的判定），端主机与 DPU 都不在路径上。
3. 迁移期间的双投（新/旧位置各一份）直接复用交换机 multicast 引擎，端侧方案做不到无感双投。

### P4 可行性分析
- **目录表**：`session-ID → {当前位置, epoch, 路径 bitmap}` 精确匹配表 + register 存 epoch；表项规模 = 活跃会话数（千~万级，SRAM 宽裕）。
- **一致性**：用 **epoch 序号 + 双投**的弱一致设计（目录允许短暂 stale，旧位置把包转交新位置或丢弃由端侧重传兜底）——刻意**不做 NetChain 式全 consensus**，把复杂度砍到 8 个月可做；一致性窗口的量化分析是论文技术点。
- **双投**：Tofino multicast group 按会话动态改写（控制面或数据面触发的 group update）；单趟转发，无需 recirculation。
- **触发**：迁移事件由端侧/控制面发目录更新包（数据面直接写表，NetChain 式 write 路径），亚 RTT 生效。

### 实验设计
- **平台**：Tofino + 2~3 台民用 PC 扮演边缘节点与客户端；bmv2+Mininet 保底（目录逻辑 bmv2 完全可表达，保真度高）。
- **场景**：① 会话迁移：mobility/handoff trace 驱动迁移事件（WTP-52/103 口径），对比 controller-based 迁移（OpenFlow 式）与 QUIC 连接迁移（端侧基线）；② 多路径换路：路径质量事件驱动主路径切换（配合 CGC-12/13 的 MoQ 多路径场景）。
- **指标**：迁移窗口内错投/丢失字节数、会话中断时长（帧级黑屏时间）、目录更新延迟（vs RTT）、目录规模-内存曲线。
- **流量**：录制游戏画面推流 + 合成并发会话。

### 目标场馆
首选 **CoNEXT / ICDCS（B）**；期刊 **Computer Networks（B）**。若与 MoQ 社区接上（CGC-12/13 作者群），MMSys 亦可作为应用面出口。

### 风险与撞车检查
- **撞车**：中低。本轮搜索确认 NetChain/Pegasus 范式无媒体侧迁移；但 QUIC 连接迁移（端侧）与 SDN 切换方案众多，**差异化论证（亚 RTT + 网络侧 + 无需端配合的双投）必须写硬**。
- **风险 1**：场景真实性——"边缘云游戏会话迁移"的部署现实性可能被质疑（商用云游戏是否迁移会话？）；对策：把第一场景写成通用的"交互式媒体会话的移动性"，云游戏只是负载代表。
- **风险 2**：贡献偏工程，理论深度不足 → 把"弱一致目录的一致性窗口分析 + 双投开销界"做成分析章节补足。
- **风险 3**：与选题3 KVRoute 的表面相似（都是"交换机目录/路由"）——对象完全不同（媒体会话 vs KV 前缀），开题与汇报时要主动划清，避免组内撞题观感。
- **新颖性把握：中**。依据：范式迁移类贡献（机制已被 Pegasus/NetChain 证明），首创性在场景与弱一致设计；验证搜索无直接撞车但未做 MMSys 社区穷尽检索。
