## N1 在网 KV 前缀指纹目录 × CRAM 混合表（主线，接卷宗空白 2）⭐推荐

- **缝料**：A = llm-d KV-Cache Indexer（软件基线）+ NetCache 表结构；b = B6 look-aside（热前缀精确表 + 长尾 sketch 旁路）+ B3 哈希压缩 + 链式前缀哈希（llm-d 同款 16-token block rolling hash）；c = 前缀树失效语义（epoch tag，B5 表合并思想 + A4 只读/写分离）。
- **冲突故事**：KV 前缀命中判定必须**线速且全局**（生产 trace 理想命中 62%/54%，ATC'25）；但软件索引（llm-d 走 ZMQ 事件）有漂移且每请求多一跳控制面；交换机精确表实测 64K×16B（NetCache）放不下百万级 block → **需要 CRAM 式"TCAM+SRAM+sketch"混合内存算法**。
- **三实验**：① 对比：llm-d 近似/精确两版、vLLM 本地 prefix cache；② 消融：无 look-aside / 无失效语义 / 纯 TCAM / 纯 sketch；③ 实例分析：ATC'25 双 trace 回放 + 自建内容级重复率 trace（旧待办）。
- **坏结果出路**：若 SRAM 占用/漂移治理代价吃掉收益 → 转"在网前缀目录何时值得"分析文（测量体裁）。
- **可宣称**：首个把前缀命中判定下沉数据平面并给出混合内存表设计 + 失效语义的工作。**不可宣称**：在网缓存 KV 本体；完整 LLM 上交换机；端到端训练/推理加速 SOTA。
- **Go/No-Go**：G1（M1 末）bmv2 原型查表吞吐 < llm-d 软件路径 → 止损转分析文；G2（M2 末）命中率偏差 >5% 相对理想值 → 降级为 DPU 变体。
- **邻居/撞车**：Foresight Indexing（NCB-6，在网 B+树——对象通用索引非前缀链式）；CableCache（NPD-1，请求级去重）；llm-d（软件功能已实现——novelty 必须落在"下沉换来的"）；NVIDIA CMX（工业，路由/复用未做命中判定）。
- **硬件**：Tofino 真机（主力）+ bmv2（大规模 trace）。

## N3 zram 建模 × BF-2 KV 卸载放置（最安全低成本，测量/建模文）⭐推荐并行

- **缝料**：A = zram（C1-C4 框架 + 模拟器）；b = **BF-2 platform graph**（zram 只建了 BF-3——BF-2 的 zone 参数没人建，C6 自认）；c = 三个 KV program graph（KV 打包/前缀目录查询/去重指纹）。
- **冲突故事**：DPU 上 KV 卸载设计目前靠"试错+直觉"（ShadowServe 自认瓶颈是 BF-3 内存子系统却无处预测）；zram 作者 agenda 明写"硬件验证 + 更多应用"——**第一个把 KV 卸载放置变成可计算问题**。
- **三实验**：① 复现：zram 已有 BF-3 案例（DDoS/DT/RDMA traversal）校准误差；② 测量：BF-2 全 zone microbenchmark 建图（内存带宽阶跃、κ、宽度）；③ 预测 vs 实测：三个 KV program graph 的瓶颈命名命中率。
- **坏结果出路**：预测误差 >2× 的场景做误差归因——**误差模式本身就是发现**（测量文天然免疫"指标碰运气"）。
- **可宣称**：首个 BF-2/BF-3 KV 卸载放置模型与实测校验。**不可宣称**：新硬件/新机制/新模型（模型是 zram 的，我们是应用+验证+扩展）。
- **Go/No-Go**：G1 BF-2 测量发现 zone 行为与 zram 假设结构性不符（如 κ 阶跃不存在）→ 改作"BF-2 测量报告"短文。
- **邻居/撞车**：zram（NCB-12，2026-09，跟进其 agenda 属正当）；Alkali（NCB-38 题录，可移植性——它是编译器不是模型）；风险低。
- **硬件**：BF-2（实验室已有）+ 纯 Python 模拟器（Windows 可跑）。

## N6 INA 增量部署收益重估（泼冷水/审计体裁，诚实出路型）

- **缝料**：A = Rina 的 BOM 模型（E8）+ Revisiting INA（NCB-2，待精读）；b = 统一 testbed 重测 SwitchML/ATP/Rina 三系在**部分部署 INA 交换机比例**下的收益曲线；c = zram roofline 视角解释曲线形状。
- **冲突故事**：INA 论文都按"全网部署"报收益，但现实是渐进部署（Rina 自己以增量部署为卖点）——**收益-部署比例曲线没人实测过**。
- **三实验**：① 三系复现（公开代码/trace）；② 部署比例扫描（0/25/50/75/100%）；③ 成本模型拟合（BOM vs 实测偏差归因）。
- **坏结果出路**：**这就是坏结果变论文的体裁**——收益若在低部署比例下消失，是强泼冷水；若不消失，是正面确认。两头都有话讲。
- **可宣称**：首个 INA 增量部署收益实测。**不可宣称**：新 INA 算法。
- **Go/No-Go**：G0 先精读 NCB-2 确认其重估范围未覆盖部署比例（**撞车检查第一优先**）。
- **硬件**：bmv2/Mininet + 公开 trace（Windows 可跑度待验证）。

## N4 Shesha 队列操作 × KV 控制面聚合（机制移植，需求待证）

- **缝料**：A = SheshaQueue（E1-E3 聚合/替换/丢弃三路）；b = 聚合对象换成 KV 控制消息（block 驱逐通告/预取请求/分片 ACK——卷宗空白 6）；c = E4 反向信令把队列状态喂给调度器。
- **冲突故事**：agentic 场景 KV 控制消息风暴（DualPath 侧证），控制面聚合没人做；Shesha 证明了"队列内按 key 聚合"的硬件可行性。
- **三实验**：① 需求测量（控制消息占比/风暴形态，agentic trace）；② 对比：无聚合 vs Shesha 式聚合；③ 消融：三路操作各自的贡献。
- **Go/No-Go**：**G0 先测需求**——控制消息占比 <5% 流量 → 故事不成立，直接止损（这就是"先证冲突再缝"）。
- **硬件**：Tofino + bmv2。

## N2 Presto 三招 × KV 传输协议上 RMT（工作量大，备选）

- **缝料**：A = Presto（A1-A8 全套，其 §5.3 已证块可复用）；b = KV 定向大块传输语义（A5 区间跟踪→KV 分片跟踪；A6 credit→KV 流配额）；c = F7 INT 协调选路。
- **冲突故事**：TCP 能上 RMT，KV 传输（语义更简单的定向大块协议）应该更能上——host CPU 从 KV 搬运中解放（PD 分离痛点）。
- **风险**：ShadowServe（网卡取回+解压）和 Presto 本身都占了相邻格；工作量是 N1 的 2-3 倍；**建议只作为 N1 的传输层后续**，不独立开篇。

## N5 Parasol × 表参数自动调优（子实验，不独立成文）

- 把 N1 的表参数（look-aside 尺寸/sketch 行列/热集阈值）交给 Parasol（C5）按 trace 自动调——作为 N1 评估方法加分项，也顺带回答"手工调参偏差"质疑。
