### A 组要点提炼（可直接复用的论证骨架）

1. **"先刻画、后卸载"是默认套路**（A-4 iPipe、A-7、A-8、A-19）：先给一张器件/通路的能力底表，再谈该卸什么。用户的"三代协议 × 卸载"天然适合这个套路，但**必须把它升格为"参数化底表 + 判决规则"，而不是三点柱状图**。
2. **基线必须包含"最强软件实现"**：A-9 同时给 Linux / TAS / 商用 TOE 三条基线；C-4（ATC'25）把 6 个栈放在同一负载下。只对内核栈说话会被认为 cherry-picking。
3. **必须有一句"前人只卸了半层"**：A-11 Strega 的原话（TCP/IP 以下已成熟、更高网络层支持缺失）+ C-9 EPIQ'20（QUIC 卸载此前只做了 crypto 模块）——这两句合起来就是用户选题的**动机段落骨架**。
4. **PCIe 是被反复独立确认的核心约束**：A-5、A-16、A-12、A-18、A-19 五个独立来源都指向同一件事。

### B 组要点提炼

**（1）资源报告：绝对量 + 归一化量，两套都要给**

- **绝对量**（必须给全）：器件型号 + 速度等级、Vivado/Vitis 版本、LUT / FF / BRAM / **URAM** / DSP、`Fmax`（不是综合目标频率，是布局布线后实测频率）、DDR4 通道与实测带宽。
- **归一化量**（现有惯例）：`LUT/Gbps`、`BRAM/Gbps`、`DSP/Gbps`、`Gbps/W`、`每连接字节资源`。
- **⚠️ 未检索到**专门"批评 FPGA 资源比较不公平"的方法论文献（多组关键词 S2/Crossref 命中 0/噪声）。**这既是本方向的文献空白，也意味着用户不能指望"引一篇现成的公平性论文"来撑腰——需要自己建立口径并显式声明为什么这样选。**
- 建议引入的**反例意识**（写进论文的 Threats to Validity）：
  - 只报加速比不报资源 → 被质疑"用无限资源换性能"；
  - 只报资源不报频率 → 低速设计显得"省资源"；
  - 只在单一器件上比 → 资源占用与器件规模耦合，不可外推。
  - **对策：报 (资源, Fmax, 吞吐) 三元组并给"资源-吞吐帕累托前沿"，而不是单点柱状图。**

**（2）能耗口径：至少四问**

现有可引的做法（B-1~B-8）覆盖了这几个层面，建议逐条显式声明：

1. **分子是什么**：per-packet（B-2）／per-byte（B-2）／per-useful-bit（B-1）／per-request（本方向需要新造）；
2. **边界在哪**：只算 FPGA 器件功耗，还是含 DDR4、收发器、风扇的**整卡功耗**？是否含主机 CPU 侧功耗？（B-7/B-8 用 SLO+TCO 把主机侧拉进来）
3. **怎么测**：Vivado 后实现功耗报告的**估算值**（vector-based / SAIF）与板级**实测**（分流电阻、功率计）必须分开标注——两者差 10–30% 是常态；
4. **基线怎么扣**：是否扣除 **idle 功耗**（同 bitstream 空转）？测量时长与采样率是多少？

| Gen3 单 lane 线速 | 8 GT/s（128b/130b）→ **7.87 Gb/s** 物理层可用 | A-18 原文 |
| Gen3 **x8** 物理层 | **62.96 Gb/s** | A-18 原文（8 × 7.87） |
| Gen3 x8 扣 DLL 开销（8–10%）后 **TLP 层** | **57.88 Gb/s** | A-18 原文 |
| Gen3 x8 实测可用 | 常 **≤50 Gb/s**，随传输尺寸锯齿波动可达 10% | A-18 原文 |
| Gen3 **x16 外推**（按同比例） | 物理层 ≈**125.9 Gb/s**、TLP 层 ≈**115.8 Gb/s** | ⚠️**笔者的等比例外推，非原文数字** |

**结论线**：如果 FPGA 靠主机经 PCIe 喂包，**上行+下行合计的有效上限在 100 Gbps 量级（且扣掉协议开销与描述符往返后更低）**。因此——
- 若实验设计让 100 GbE 流量穿过主机再回 FPGA，则 **PCIe 会先于三代协议的差异饱和**，横评结果被上限吞掉；
- 正确做法是 **FPGA 直连网络**（片上 100G MAC / 128 路 GTY），让协议栈实现在**网络侧**，PCIe 只承担控制面与统计上报——这正是 A-12 的论点，也是 A-19/B-9 反复指认的瓶颈。
- 另一条腿：用户板载 DDR4 弱 → **每连接状态必须尽量压在 URAM/BRAM（≈57 MB 总量）里**。这个容量恰好是"HTTP 响应体/头部缓存"尺度，值得作为边界模型的关键参数。

## 本子领域结论

### 一、卸载研究"为什么上硬件"的标准论证结构（可复用模板）

现有 A 组范本的论证骨架高度一致，可归为 **7 个必答要素**。用户的选题若只做"三代横评"，等于只回答了 (1)(2)(3)，而 (4)–(7) 恰好是 CCF-B 审稿人真正看的东西。

1. **成本现状（为什么要处理它）**
   用"datacenter tax"框架给出目标功能占主机 CPU 的份额与增长趋势。可引 A-4 / A-5 / A-10 / A-13；若要把主机侧算进来，引 B-7 / B-8 的 SLO+TCO 框架。
2. **软件已到极限（为什么不能靠优化软件解决）**
   必须给出"最强软件基线"的实测数字：内核栈、DPDK、以及专为 HTTP 优化的用户态栈。可引 A-9（Linux/TAS/Chelsio 三方对比）、C-4（6 栈横评）、C-5（DPDK vs XDP）。**缺这一步，全文作废。**
3. **既有卸载工作的能力边界（为什么前人没解决）**
   一句"只卸了半层"的判决。Strega（A-11）的原话可直接用：*TCP/IP 这一层的硬件卸载已很清楚，但更高网络层的加速器支持仍然大量缺失*。再加 C-7：*QUIC 的卸载此前只考虑了 crypto 一个模块*。
4. **本层特有的结构障碍（为什么难）**
   不要说"更快"，要说"这一层的语义让现有卸载抽象表达不了"：HTTP/1.1 的每连接长生命周期 + keep-alive 状态；HTTP/2 的 **HPACK 动态表**（有状态、跨流共享、顺序敏感，天然难并行）；HTTP/3 的连接迁移、多流复用、0-RTT、以及 QUIC 的包重排序（C-7 已指认其为 CPU 大户）。**这一节是用户最容易做出"方法学贡献"的地方。**
5. **资源与通路约束的定量化（为什么要重新设计而不是直接搬）**
   PCIe 墙（A-18 原文：Gen3 x8 TLP 层 57.88 Gb/s、实测常 ≤50 Gb/s；x16 等比例外推 ≈115.8 Gb/s TLP 层——**外推须自标**）、板载内存带宽（用户 DDR4 弱）、片上存储预算（VU13P ≈455 Mb ≈57 MB，B-13 待核实）、可编程加速器的实际能力（A-8 的 DPA 比 ARM/CPU 更弱这一反直觉事实）。
6. **代价模型 / 卸载边界（本研究的真正贡献位）**
   给出**可判定**的规则，而不是经验观察。形式建议：`卸载净收益 = f(连接数, 每连接状态字节, 净荷分布, PCIe 可用带宽, 片上存储预算) > 0 ?`。**这个空白是 A-17（Clara, HotNets'20）明确点出、至今没有成熟答案的**——可作为"我们填的是谁的坑"来引用。
7. **可反驳性**
   把结论写成可被后续实验否证的形式，例如"当并发连接数 × 每连接 HPACK 动态表 > 片上 URAM 的 N% 时，HTTP/2 的卸载收益转负"。CCF-B 的测量/刻画类论文（A-8、A-19）都以这种断言收尾。

### 二、FPGA/网卡资源与能耗的报告规范建议（含可引做法）

**资源（两条线，缺一不可）**

- 绝对量：器件型号 + 速度等级 + 工具版本（Vivado/Vitis 版本号）+ 综合/实现策略；LUT、FF、BRAM、**URAM**、DSP、**布局布线后实测 Fmax**、DDR4 实测带宽。
- 归一化量：`LUT/Gbps`、`BRAM/Gbps`、`DSP/Gbps`、`Gbps/W`、`每连接资源`。
- 呈现方式：**报 (资源, Fmax, 吞吐) 三元组 + 资源-吞吐帕累托前沿**，不要单点柱状图。
- 可引做法：A-15 Sidler（早期范式）、A-10 F4T、A-14 Corundum（开源平台、可复现）、A-16 Honeycomb、B-12（面积-能效双口径）。
- **诚实声明**：本轮**未检索到专门批评"FPGA 资源比较不公平"的方法论文献**（S2 + Crossref 多组关键词命中为 0 或纯噪声）。这意味着用户必须**自己立口径并解释理由**，不能靠引文豁免。建议在 Threats to Validity 里显式写出三种常见不公平（只报加速比不报资源／只报资源不报频率／单一器件外推）并逐条给出对策。

**能耗（四问必须逐条回答）**

1. 分子：per-packet / per-byte（B-2）、per-useful-bit（B-1）、per-request（本方向需新造）；
2. 边界：仅器件？含 DDR4+收发器的整卡？含主机 CPU？（B-7/B-8 的 SLO+TCO 口径可引）
3. 测法：**Vivado 后实现报告的估算值**（须注明 vector-based / SAIF）与**板级实测**（分流电阻/功率计）必须分开标注；
4. 基线：是否扣除 idle 功耗、测量时长、采样率。
- 可引做法：B-2 / B-3 / B-4 / B-5（FPGA 网络设备能耗的四篇直接先例，其中 **B-3 发在 Computer Networks，是 CCF-B 期刊**）；B-6（TCC'17，指标口径论文，CCF-B）。

**PCIe 账本（必须写进论文的约束节）**

- 原文可引数字（A-18）：Gen3 单 lane 7.87 Gb/s；x8 = 62.96 Gb/s 物理层；扣 8–10% DLL → 57.88 Gb/s TLP 层；实测可用常 ≤50 Gb/s。
- 结论：**Gen3 x16 的有效上限在 100 Gbps 量级**（x16 数值为等比例外推，须自标）。
- 设计含义：让 100 GbE 流量穿过主机再回 FPGA，会遇到 PCIe 先饱和；应让 FPGA 直连网络（片上 100G MAC / GTY），PCIe 只走控制面。板载 DDR4 弱 → 每连接状态压在 ≈57 MB 的 URAM/BRAM 预算是关键设计参数。

### 三、测量/对比类论文在 CCF-B 的贡献形态清单

见上文 C 组末尾的 5 形态表。核心先例与其贡献句：

1. **C-4 Opening Up Kernel-Bypass TCP Stacks（USENIX ATC'25，CCF-A）**——"由于这些栈很难运行，它们从未被放在同一组基础负载下比较过；我们跑通 6 个栈并给出首个可比的对比。"（最贴近用户意图，级别最高）
2. **C-1 Taking a Long Look at QUIC（IMC'17，CCF-B）**——"我们表明，此前 QUIC 与 TCP 的对比因方法问题不可比；我们提出严谨评估方法并给出新结论。"
3. **C-3 Comparing DNS Resolvers in the Wild（IMC'10，CCF-B）**——"我们首次对多个公共解析器做统一负载下的性能与正确性横评，给出相对排序及影响因素。"
4. **B-6 Fiandrino et al.（IEEE TCC'17，CCF-B）**——"我们梳理并统一了云数据中心通信系统在性能与能效上的指标口径，指出既有指标的适用边界。"
5. **C-2 Replication: Taking a long look at QUIC（IMC'24，CCF-B）**——"我们用 7 年后的软硬件重做该实验，发现原结论的条件依赖性。"（IMC 有正式 replication 赛道）
6. **A-8 Demystifying DPA（ICNP'24，CCF-B）／A-19 BlueField DPU 刻画（ICS'25，CCF-B）**——"首个系统刻画 + 反直觉结论 + 设计指南。"

### 四、对用户点子的直接判断

**判断一：只做"HTTP/1.1(TCP) vs HTTP/2(TCP+HPACK) vs HTTP/3(QUIC) 三代协议在 FPGA/NIC 上的横评"，天花板大概是 CCF-C。**

依据：
- "同功能多平台端到端对比"这一形态的现成先例 **C-6（NOMS'25 无状态防火墙四实现横评）** 与 **C-5（CCR'23 DPDK vs XDP）**，级别都不构成 CCF-B；
- 软件侧的 HTTP/3 测量已经落地在 **C-8（Computer Communications, CCF-C）**、Quantifying 的浏览器级测量落在 **C-9（TNSM, CCF-C）**——**"HTTP 协议横评"这个赛道的期刊出口已被占并且天花板不高**；
- 硬件侧的近邻位已被 **A-11 Strega（FPGA 上跑 HTTP 服务器，TRETS/CCF-B）** 与 **C-7 EPIQ'20（QUIC 卸载 primitives）** 占据，纯横评的"新"只在组合，不在方法，且**缺少可证伪的边界结论**。

**判断二：要上 CCF-B，必须补三件事（缺一不可）。**

1. **一个可判定的卸载边界 / 代价模型**（对应 A-17 Clara 点出、至今未解的空白）。
   形式：给出 `净收益(连接数, 每连接状态字节, 净荷大小分布, PCIe 可用带宽, 片上存储预算, 能耗口径) > 0` 的判决规则，并在三代协议上分别验证与**否证**。这是把"横评"变成"方法学贡献"的关键一步。
2. **一套统一口径 + 帕累托前沿**（对应形态 ④，先例 B-6 / B-3）。
   不是三根柱状图，而是 `(per-Gbps LUT/BRAM/URAM/DSP, Gbps/W, per-connection bytes)` 的资源-吞吐-能耗前沿，并在论文中把口径选择本身作为可讨论的贡献。
3. **一个可证伪的反直觉结论**（对应形态 ③，先例 A-8 / A-19）。
   例如："QUIC 卸载的绝对收益最大但资源效率最差"、"HTTP/2 因 HPACK 的跨流动态表使卸载代价反而高于 HTTP/3"、"当连接数超过 N 时 HTTP/1.1 的卸载收益由正转负"。**没有这种句子，CCF-B 会判为"工程对比报告"。**

**判断三：三个会直接杀死实验设计的坑。**

- **PCIe 墙**：若 FPGA 经主机 PCIe 喂包，Gen3 x16 的有效上限约 100 Gbps（x16 为外推值），三代协议的差异会被上限吞掉。**必须让 FPGA 直连网络（100G MAC/GTY），PCIe 只走控制面**（A-12 + A-18）。
- **不公平基线**：必须包含内核栈、DPDK、以及**专为 HTTP 优化的用户态栈**三条；否则重蹈 C-1 批评的那类错误。
- **资源不可比**：三代协议的状态模型完全不同（HTTP/1.1 每连接缓冲、HTTP/2 HPACK 动态表、HTTP/3 多流 + crypto + 重排序），必须归一化，**且本轮没有现成的"公平比较"论文可引**——需自立口径。

**判断四：目标场馆需按官方目录重排（任务书的假设有错）。**

- ❌ **TACO 不是 CCF-B，官方第七版是 A 类**（与 TOCS/TOS/TCAD/TPDS 同块）；把它当"B 类保底期刊"会误判投稿定位。
- ❌ **PAM 不是 CCF-B，是 C 类**（位于"网络与信息安全"领域 C 类会议列表）；**TMA 与 ACM CCR 都未收录于第七版**。
- ✅ 可行的 CCF-B 目标（逐条核对过官方 PDF）：**IMC**（测量/横评最对口）、**ICNP / CoNEXT**（系统与网络）、**FPGA / ICCD / DATE**（硬件实现）、**TRETS / Computer Networks / TCC / JPDC**（期刊）、**ICS**（体系结构刻画）。
- 由此，投稿策略建议：**硬件实现侧投 FPGA / ICCD / DATE，测量与代价模型侧投 IMC / ICNP，期刊侧投 TRETS 或 Computer Networks**；两端并行比"押一个横评投 Computer Networks"成功率高得多。
