> **B 组小结（直接回答"TLS 卸载成熟到什么程度"）**：
> 1. **记录层（对称加解密）卸载：已生产化、成熟。** 通道 = kTLS `TLS_HW` 模式 + 网卡 inline crypto（ConnectX-6 Dx 及以后；BF-2 datasheet 明确列 TLS/IPsec inline）。软件栈要求明确（Linux 5.3+/5.9+，OpenSSL 3.2.0+）。厂商侧有 QAT（scale-out）与 ConnectX/BlueField（inline）两条路线。
> 2. **握手卸载：没有真正"卸到硬件"。** 三方证据一致：NVIDIA DOCA 明写 `HW-record`（含握手）**当前不支持**；Linux 内核文档明写 `TLS_HW_RECORD`（网卡自带 TCP）**不可用于生产**；Autonomous NIC offloads（ASPLOS'21）的设计就是"握手留在软件"。QAT 只**加速**握手里的非对称运算（QTLS, PPoPP'19），握手状态机仍在 CPU。
> 3. **还有一条被忽略的分界线**：**kTLS 只作用于 TCP**。QUIC 的 TLS 1.3-over-UDP 走不进 kTLS 卸载通道（C 组详述）。

> **C 组小结（回答"QUIC 有没有被做进硬件"）**：
> - **完整 QUIC 服务端栈进 FPGA：没有**。arXiv `all:"QUIC" AND all:"FPGA"` = **0 命中**（元数据级）。
> - **QUIC 客户端 IP 核：工业界已有商品**（L7H-44，Design Gateway，1 GbE，CPU-less）。
> - **QUIC 的密码学/分段卸载：有接口提案、未成主流**（Intel Netdev'19，L7H-36）。**核心技术障碍**：QUIC 头本身被加密，硬件无法在不解密的情况下解析帧——这一条同时解释了为什么 QUIC 卸载做不动，也解释了为什么 HTTP/2 的 HPACK、HTTP/3 的 QPACK 难以独立硬件化。
> - **QUIC 的内核旁路：2026 年还有人在问"值不值"**（L7H-38）。
> - 注意：5G UPF / 边缘网关侧的卸载**不是 QUIC**，是 **GTP-U/SRv6**（见 G 组），没有检索到把 QUIC 做进 UPF 硬件的论文。

## 本子领域结论

### 结论一：HTTP 栈分层 × 已否有硬件实现（对照表）

| 栈层 | 已有谁做了 | 做到什么程度（含数字） | 剩余空白 |
|---|---|---|---|
| **L4 传输（TCP）** | 最成熟的一层。学界：AccelTCP（NSDI'20，状态机卸载）、FlexTOE（NSDI'22）、PnO-TCP（2025）、ContaTOE（2026）；工业：TOE IP 核（Design Gateway / HiTechGlobal 商用）、Catapult 自带轻量传输 | **可卸载状态机、可线速**；AccelTCP 已把 TCP 状态机（非仅搬运）放进网卡，应用几乎不改。但反方 Mogul HotOS 2003 的批评至今未被彻底驳倒。**注意：用户手上的 XCVU13P 无 HBM + PCIe Gen3 ×16，而 PCIe 已是端主机网络的真实瓶颈（Neugebauer, SIGCOMM'18，本工作区 DBK-49）** | 与"HTTP 卸载"关系不大——这层基本是**红海**，且不是三代协议差异所在 |
| **TLS 记录层（对称加解密）** | **已生产化**。工业：kTLS `TLS_HW` + ConnectX-6 Dx/BlueField inline crypto（DOCA 官方）；Intel QAT（F5 白皮书 128 B 包 34,173 vs 3,660 TPS ≈ 9.3×）；NVIDIA BF-2 datasheet 明列 TLS/IPsec、AES-GCM、SHA、公钥加速器。学术：Autonomous NIC Offloads（ASPLOS'21）、XTLS（APSys'26） | **成熟**。但**只在 TCP 上**：kTLS 是 TCP ULP，**覆盖不到 QUIC 的 TLS-over-UDP** | ① QUIC 的记录层加密卸载（无成熟通道）；② kTLS 对隧道/虚拟接口的 socket 不卸载（5-tuple 限制） |
| **TLS 握手层** | **没有真正的硬件卸载。** QAT 只**加速**非对称运算（QTLS, PPoPP'19），握手状态机仍在 CPU；Switch 侧只做 **SNI 明文提取**（ICC/NOMS'25，线速，定长字段） | **未落地**。三方独立反证：DOCA 官方明写 `HW-record`（含握手）**当前不支持**；Linux 内核文档明写 `TLS_HW_RECORD` **不可用于生产**；ASPLOS'21 的设计就是"握手留软件" | **真空白**：握手全硬件化（尤其是能扛 rekey/KeyUpdate/异常路径的状态机） |
| **HTTP/1.1 解析（请求行/头部）** | 弱。Strega（TRETS，FPGA 上**完整 HTTP 服务端栈**，延迟 16 µs vs nginx 108 µs）；Blott HotCloud'13 的 request parser；一批嵌入式 FPGA web server（2012–2018，低影响力） | **能跑，但只做了一代最简单的协议**。Strega 是唯一有系统评测的开源实现 | HTTP/1.1 本体接近"已做"；但**从没有人把它和 /2、/3 放在同一硬件平台上比过** |
| **HTTP 解析做进可编程交换机** | Miresga（WWW'25：**3.9× 吞吐、0.4× 延迟**，但**HTTP 内容解析留在 front-end server**）、L7LB（INFOCOM-W'23）、P4DDPI（DNS 变长解析的可为与不可为） | **只做 L4/L7 的"转发与建连"，HTTP 语义仍在 CPU。** 交换机受限于 P4 的变长解析能力（P4DDPI 结论）与片上内存（NetCache 8 MB / 16 B key） | **HTTP 语义真正进数据平面**（不是转发，而是解析 + 路由决策） |
| **HPACK（HTTP/2 头部压缩）** | **无。** arXiv `abs:"HPACK"` = 0；S2 `"HPACK decoder implementation"` = 0（返回全是 LDPC/Polar 解码器）；S2 `"HTTP/2 header compression hardware implementation"` 仅 RFC 与 1 篇低质量期刊 | **零硬件实现。** 且 HPACK 是**有状态、动态表、依赖 Huffman 与索引增量更新**的串行解码器——与 FPGA 擅长的定长流水线天然不合 | **真空白**（也可能是"硬件上本来就不该做"的空白） |
| **QPACK / HTTP/3 帧解析** | **无。** arXiv `abs:"QPACK"` = 0（唯一命中是量子计算 QPack）；arXiv `all:"HTTP/3" AND all:"FPGA"` = 0 | **零硬件实现**（只有 Design Gateway 的**客户端** QUIC IP 核，1 GbE，商品 IP，非学术） | **真空白**。障碍是结构性的：**QUIC 头本身被加密**，硬件不解密就看不到帧类型/流 ID |
| **请求路由 / L7 负载均衡** | 最热闹的一层。软件：Ananta（SIGCOMM'13）、Hermes（SIGCOMM'25）、XLB（eBPF, 2026）；交换机：Miresga（WWW'25 / IEEE TC'26）、L7LB；DPU/硬件：Tiara（NSDI'22，L4） | **"路由决策下沉"已在做**，但**HTTP 感知的部分（URL/header 匹配）基本都还在 CPU**。Miresga 是最诚实的架构：交换机只负责 FAST PATH 的建连与改写 | 把 **HTTP 语义匹配**（URL/header/方法）真正放进硬件的数据平面 |
| **缓存（对象/响应缓存）** | 几乎没有。交换机侧只有 **KV 缓存**（NetCache SOSP'17、OrbitCache NSDI'25），**不是 HTTP 对象缓存**且容量受限严重（8 MB、16 B key；54 个真实 workload 中 42 个连一条都放不下）；HTTP 对象缓存仍在软件（nginx/Varnish） | **可编程交换机放不下 HTTP 对象。** 有 2000 年的硬件 vs 软件 web proxy 缓存对照论文（Waldhorst 2000），此后无声 | **HTCP/HTTP 对象缓存进硬件 = 真空白**（且从容量看是幻想层；若要碰，只能做"元数据/热度索引"而不是对象本体） |

### 结论二：最危险的邻居论文（若用户立题，最可能撞谁）

按"撞车危险度"排序：

1. **Strega（L7H-1，ACM TRETS，github.com/fpgasystems/strega，ETH Zürich）** — **危险度最高**。它已经把"整个网络栈 + HTTP 服务端栈卸载到 FPGA"做出来且开源。如果用户的贡献表述为"在 FPGA 上实现 HTTP 服务端"，**直接撞死**。差异化只能落在：**多代协议对比本身**（Strega 只有 HTTP/1.1 一代）。
2. **Miresga（L7H-4/5，WWW'25 + IEEE TC'26）** — 如果用户把点子讲成"交换机/硬件做 L7 负载均衡"，**撞车**。它的架构诚实说明"HTTP 解析留在 CPU"，正说明该缺口还在。
3. **Making QUIC Quicker With NIC Offload（L7H-35，EPIQ@SIGCOMM'20）+ Intel Netdev'19（L7H-36）** — 如果用户讲成"给 QUIC 设计硬件卸载原语"，**撞车**。这两篇已经把"该卸载什么、接口长什么样"论证过了。
4. **XTLS（L7H-22，APSys 2026）** — 如果用户讲成"TLS 卸载的栈协同设计"，**撞车**，而且是 2026 年的最新态。
5. **Scallop（L7H-61，SIGCOMM'25）** — 如果用户讲成"把某个 L7 应用的数据面拆成硬件数据面 + 软件控制面"，**架构撞车**（Scallop 是视频会议 SFU，不是 HTTP，但方法论同一套，且它已经发在 SIGCOMM）。
6. **Autonomous NIC Offloads（L7H-16，ASPLOS'21）** — 方法学邻居。若用户做 kTLS 相关硬件，这篇是绕不过的 baseline。
7. **AccelTCP（L7H-91，NSDI'20）+ Mogul HotOS'03（L7H-92）** — 一个给"协议状态机进硬件"的正面证据，一个给反面论据。**审稿人几乎必然引这两篇**，必须提前回应。

### 结论三：对"三代协议横评"命题的可行性判断

**总判断：这个命题的"横评"部分有真实的学术空白，但用户设想的"三代协议栈横评"在硬件上绝大部分是不可实现的；可行的那一小块，恰恰是价值最低的一块。**

**分层判定：**

| 层 | 硬件可行性 | 理由 |
|---|---|---|
| L4：TCP（HTTP/1.1、/2 的载体） | ✅ **现实** | 有成熟 IP 核、开源栈（Strega 底座、ContaTOE、Alveo 参考设计），XCVU13P 完全跑得动 |
| L4：UDP + QUIC 拥塞控制/丢包恢复 | ⚠️ **半现实** | 包头可解析、ACK/重传逻辑可做，但**帧类型与流 ID 在加密区内**，硬件必须"先解密才知道在解什么"。这是结构性障碍，不是工程量问题 |
| TLS 记录层加解密 | ✅ **现实（且有现成件）** | AES-GCM 在 FPGA 上是常规件；但**学术贡献已近枯竭**（ASPLOS'21 + XTLS'26 已占位） |
| TLS 握手 | ❌ **幻想（对毕设规模）** | 全行业都没做（DOCA 明说不支持、内核文档明说不可生产）。握手含非对称运算、证书链验证、异常路径、rekey；工程量与验证成本远超一学期 |
| HTTP/1.1 请求解析 | ✅ **现实** | 定长/可枚举、无状态、字符串匹配，硬件友好。Strega 已证 |
| **HPACK（HTTP/2）** | ⚠️ **技术上可做，但很难、也难说是"该做的"** | HPACK 有**动态表 + 增量索引 + Huffman**，是串行有状态解码；可以做，但流水线收益小、状态复杂度高。**且这是真空白——没有前人工作可参照，风险高** |
| **QPACK（HTTP/3）** | ❌ **基本不可行** | ① QUIC 头加密 → 硬件看不到帧边界；② QPACK 依赖 QUIC 的流控与乱序到达语义（单向流 + 动态表同步），其"解码阻塞"恰恰是设计特性。**把 QPACK 单独抽出硬件化在语义上就错了** |
| HTTP/2 帧层多路复用 | ❌ **不可行** | 帧复用/优先级/HOL 是**逐流状态机**，硬件化的代价超过收益，且需要与 HPACK 联合 |
| HTTP/3 帧层 | ❌ **不可行** | 同 QPACK，且多一层加密 |
| 请求路由（URL/header 匹配） | ✅ **现实** | 正则/多模式匹配在 FPGA 上很成熟（本工作区 NPD-15）；BF-3 甚至有 75 Gb/s 的 RegEx 引擎可对照 |
| 缓存 | ❌ **幻想** | 可编程交换机 8 MB 放不下 HTTP 对象；FPGA 的片上 ~57 MB（用户 XCVU13P）虽大得多，但 DDR4 带宽弱、无 HBM，缓存命中的收益会被内存带宽吃掉 |

**给主代理的三条建议：**

1. **别做"三代协议栈横评"。** 用户设想的形式（三套协议栈都进硬件、同平台横评）在结构上不成立——QPACK/HTTP/3 帧层因为 QUIC 头加密**无法成为独立的硬件模块**。硬要做，只能做成"L4 卸载 + TLS 记录层卸载 + 上层仍在软件"，那时三代协议的差异**几乎全部发生在软件层**，硬件平台只是个共同底座，横评结论不成立于硬件。
2. **真正可能立住的命题是"**卸载边界**"问题，而不是"三代横评"问题。** 明确的、有文献支撑的空白是：**"哪些 HTTP 栈层卸载到硬件是划算的、边界在哪里？"**——Miresga 给出了部分答案（HTTP 解析留 CPU），DOCA/Linux 给出了 TLS 的答案（记录层可卸、握手不可），**但没有人把这三代协议的卸载边界做成一张一致的、可测量的对照图**。把命题从"横评比性能"改成"**卸载边界与代价模型**"，既有空白、又能解释 Strega/Miresga/DOCA 三方为什么各自选在不同的地方切刀。
3. **最危险的现实约束不是学术，是硬件。** XCVU13P **无 HBM、板载 DDR4 带宽弱、PCIe Gen3 ×16**（本工作区 DBK-49 已量化 PCIe 才是端主机网络的真实瓶颈）。这意味着**吞吐型**的横评会被 PCIe 卡死，横评数字区分不出协议差异。若坚持做，必须把评测设计成**时延/资源占用导向**而非吞吐导向。
