## C. 差异化判断（原始证据与推理，结论见文末）

> 本节不引入新条目，只做基于 A/B 两组的推理，**每条都指回上面的编号**。

**C-1 RK3588 上"与协议栈有关的硬件"到底只有两样。** 一颗 MAC（DWC_ether_qos GMAC 4.20a，RK-A21/A22）+ 一颗 crypto/PKA 引擎（RK-A1/A3/A4）。其余加速器（NPU 6 TOPS、VPU、RGA）与网络协议栈无关：NPU 是静态算子图执行器（本工作区既有结论），不表达 HTTP 解析/HPACK/QPACK 这种状态机。
**⇒ 「HTTP 协议栈卸载」里的 传输层状态机、HTTP 解析、头压缩 三块在 RK3588 上完全没有硬件。**

**C-2 唯一"可能有用"的那块硬件，恰好大部分被证伪。**
- 覆盖率：**只有加密/认证**（对称 + 公钥 + 哈希），对 TLS 记录层（AEAD）和握手密码学都有算法（A1/A4）。**没有**解压、没有协议解析、没有正则、没有交换/分流。
- 但**内核优先级 0**（A5）vs **ARMv8 CE 的 300**（A6/A7），而 kTLS 软件路径就是按优先级选 AEAD（A8）⇒ **内核根本不选它**。
- **kTLS 的硬件 record offload（`TLS_HW`/`TLS_HW_RECORD`）在 RK3588 上不可用**，因为那是 netdev 层能力而 stmmac 没有 TLS 卸载接口（A9）。
- 真要用，只能绕到**用户态 cryptodev/librkcrypto**（A13），而厂商自测显示引擎上限 **AES-256-GCM 310 MB/s、ECB 716 MB/s、SHA-256 316 MB/s**（A10），**而同一颗芯片一个 A76 核用 ARMv8 指令就有 AES-256-GCM 1,763.9 MB/s / AES-128-GCM 2,185.7 MB/s**（A18）⇒ **引擎比 CPU 指令慢约 5.7×（AES-256-GCM）**。加密引擎还会因对齐/长度/SG 限制大量退回 CPU（A16）与 A5/A20 的机理一致（DMA 往返延迟）。
- 公钥侧反差更极端：引擎 **RSA-2048 私钥运算 105 ms**（A10，≈9.5 次/秒），而 CPU 上 OpenSSL **RSA-2048 签名 269.6 次/秒**（A18，≈3.7 ms）——**约 28× 的差距**。⚠️ 两者口径不同（librkcrypto 的计时包含其自身的 bignum 实现路径，未必是 PKA 硬件纯耗时），**不能直接当加速比，标"口径待核实"**；但"引擎在公钥侧毫无优势"这个方向性结论是可用的。
- 主线支持：**2026-05 的补丁系列仍只做 AES+XTS+hash、且 AES-CBC 实测 ~100 MiB/s、尚未合并**（A14/A15）。⇒ **"RK3588 硬件 crypto 卸载"在 2026 年是一个"存在但落后"的技术。**

**C-3 它给不了 FPGA/DPU 那种"数据面可编程"。** 无可编程逻辑 ⇒ 不能做 RTL 卸载、不能自定义解析器、不能做 HPACK/QPACK 硬件解码器。GMAC 侧：厂商 BSP 单队列（A23），无 RSS/多队列分流；官方 DPDK 文档支持列表里最快要靠外挂 Intel I210/I350 或 RTL8111H（A25），且 **GMAC DMA 只能访问 4 GB 以下物理内存**（A26）；PCIe 侧还有 **DMA 一致性需手工维护**（A27）。⇒ **吞吐天花板现实：单/双 2.5GbE + 几百 Mbps~1 Gbps 级小包转发**（A25/A26 的 RK3568 数字：64B 转发 300–580 Mbit/s@单核）。

**C-4 它给得了 FPGA/DPU 给不了的三样。**
1. **真实产品级平台**：整板空闲 4–5 W、满载 10–12 W（A30），完整 Debian + 8 核 A76/A55 + 2.5GbE（A18），是消费级路由器/网关/NAS 的**真实硬件形态**。FPGA 板（用户手上的 XCVU13P）与 BlueField 卡在功耗、价格、软件栈上都不是这个品类。⇒ 可以做**"能耗-性能曲线"与"整机成本"这两个维度**，FPGA/DPU 做起来贵且失真。
2. **同硅片上的三方对照**：**纯软件（`OPENSSL_armcap=0`，A17）** vs **ARMv8 指令（默认）** vs **硬件 crypto 引擎（cryptodev/librkcrypto）**，在同一颗 SoC、同一份 DRAM、同一套软件栈上比较 —— **不换平台、不换板卡、不换 PCIe**。n=1 的受控实验，变量干净。这是 FPGA/DPU 无论怎样都做不出的对照（A20 的定性也说明 DMA 型引擎与指令型加速有本质延迟差）。
3. **可做"应用与协议栈同机竞争"的测量**：NPU 跑推理 / VPU 转码 / crypto 引擎加密 / 8 核跑网络栈，共享 LPDDR4X（既有实测 17–22 GB/s，见本工作区《边缘端侧LLM调研》）⇒ 可以量化**"边缘节点上协议栈加速器与业务加速器抢同一份 DRAM/功耗预算"**，这是边缘场景独有、FPGA/DPU 无法复现的问题。
4. **主线内核可用性/可复现性**：相对 Rockchip BSP，主线已经支持 GMAC 多队列与 AF_XDP 零拷贝（A22/A24）；GPL 开源、社区可复现 ⇒ 论文的 artifact 可验证性优于 vendor-BSP-only 的加速器路线。

**C-5 若并入对比矩阵，最合理的角色。**
- **角色 1（首选）"现实基线 / 边缘服务器本体"**：在 RK3588 上用同一份内容分别以 H1.1/H2/H3 提供服务（2.5GbE 上限），测吞吐、CPU 占用、整板功耗。**这直接补上 RK-B1 未覆盖的三样：非手机 SBC 的吞吐/CPU 维度、真实 2.5GbE 网络、以及"能跑到什么绝对水平"。**
- **角色 2（最有新意）"硬件 crypto 引擎 vs ARMv8 指令 vs 纯软件"的三方受控对照**：A17 的 `OPENSSL_armcap=0` 给了纯软件基线；A10/A18 给了另两方的先验数字。**这个实验便宜、可复现、数字缺口明确（A18 作者本人明说没测引擎）**，且能直接判死"把 TLS 卸载到 SoC crypto 引擎"这条路在 RK3588 上是否划算。
- **角色 3（配套）客户端/对端**：作为 FPGA/DPU 侧实验的对照端点（真实 ARM 客户端），测三代协议在真实边缘客户端上的行为。
- **做不出来的**：数据面 RTL 卸载、HTTP/HPACK/QPACK 硬件解析、kTLS `TLS_HW_RECORD`、10G 线速、多队列/RSS 分流、可编程 ingress pipeline。

### 2. 最关键发现

1. **RK3588 上唯一"能碰协议栈"的硬件（crypto 引擎）比 CPU 自己的 ARMv8 指令慢约 5.7×**：引擎 AES-256-GCM **310 MB/s**（Rockchip 官方 librkcrypto 自测）vs 一个 A76 核 **1,763.9 MB/s**（TinyComputers 实测）。且 Rockchip 把该驱动的内核注册优先级设为 **0**，而 ARMv8 `gcm-aes-ce` 是 **300**，**kTLS 软件路径按优先级选实现 ⇒ 永远用 CPU，不用硬件引擎**。（RK-A5/A7/A8/A10/A18）
2. **kTLS 的 `TLS_HW` / `TLS_HW_RECORD` 硬件记录层卸载在 RK3588 上根本不可用**：这是 netdev 层接口，而 RK3588 的 GMAC（stmmac/dwmac-rk）源码里没有任何 TLS 卸载钩子。想要"HTTP 栈卸载到硬件"，RK3588 连第一层（TLS 记录层）的门都进不去。（RK-A9）
3. **硬件引擎在真实流量下大量退回 CPU**：官方 debugfs 统计显示 `ecb-aes-rk2` reqs=131 / **fallback=2005**（其中 **alignment 1649**、length 352）、`cbc-aes-rk2` reqs=154 / fallback=2164；官方未合并补丁也承认多 SG 的 hash 要退回软件。机理与 NXP SEC/CAAM 的定性一致：**DMA 型引擎对块对齐/长度敏感、延迟更高，而 ARMv8 指令就在 CPU 里**。（RK-A16, RK-A14, RK-A20）
4. **RK3588 的网络硬件天花板是"2×1GbE SoC + 外挂 2.5GbE"**：SoC 自带 GMAC 只有 10/100/1000M（数据手册明写），板卡上的 2.5G 一律是 RTL8125 走 PCIe Gen2 x1；厂商 BSP 单队列、无 RSS；**GMAC DMA 只能寻址 4 GB 以下物理内存**；PCIe 侧还要求手工维护 DMA cache 一致性。官方 DPDK 文档给出的全是 RK3568 数字（64B 转发 580 Mbit/s@单核），**RK3588 的 DPDK/AF_XDP 实测在公开渠道为零**。（RK-A21, RK-A18, RK-A23, RK-A26, RK-A27）
5. **嵌入式侧"三代 HTTP"的唯一正式前作是 Caiazza 等（PMC 2024），且它测的是能耗、不是吞吐/CPU，也没有任何硬件卸载**：M2M 场景下 HTTP/3 在 2 MB 载荷时比 HTTP/1.1 **多耗 30–36%** 能量、4 MB 时 **多 45–53%**，而且 **HTTP/1.1 与 HTTP/2 无显著差异**；作者把根因指向"HTTP/3 在用户态花的时间更多"。（RK-B1）
6. **主线内核对 RK3588 的支持是"能跑网、不能用加速器"**：GMAC 有 2 队列 + AF_XDP 零拷贝（官方源码级证据），但 **crypto 节点在主线 DTS 里都不存在**，厂商 crypto 驱动 2026-05 仍未合并、且只覆盖 AES+XTS+hash。**选内核 = 选实验能做什么**。（RK-A15, RK-A22, RK-A24, RK-A14）

### 3. 明确空白

1. ★ **没有任何公开工作做过「ARM SoC 上 HTTP/1.1 × HTTP/2 × HTTP/3 × 硬件 crypto 卸载」的对照。** 最接近的 RK-B1 覆盖了"三代 HTTP × 嵌入式客户端（手机 + 一块 SBC）"的**能耗**，但：不含吞吐/CPU 分解、不含服务器侧、**不含任何硬件卸载**、且未区分 AES-GCM 由 CPU 指令还是引擎执行。多轮 S2/arXiv 定向查询（含三组直接查询返回 0 条）未命中该交集。（RK-B16）
2. ★ **没有任何人测过 RK3588 的硬件 crypto 引擎在 TLS/QUIC 负载下的表现。** 连 2026 年那份专业评测都明确写"dedicated accelerator's throughput remains unmeasured"。已有的引擎数字全部是 librkcrypto 的裸算法 benchmark（1 MB 连续、DMA fd），**没有记录层口径（小 record / AEAD 逐块 / 握手混合）的数字**。（RK-A10, RK-A18）
3. **没有任何学术工作把 RK3588 当网络/边缘服务器本体来刻画**（学术界的 RK3588 = CV/AI 推理）。（RK-B17）
4. **RK3588 上 DPDK / AF_XDP 的公开实测吞吐为零**：只有 Rockchip 官方对 RK3568 的表（580 Mbit/s@64B 单核）和一条"GMAC 只能 4 GB 以下"的约束；主线 stmmac 声称 AF_XDP 零拷贝，但无第三方数字。同时 **DPDK 主线没有 Rockchip GMAC 的 PMD**（只有下游 fork 里有 `net_stmmac` vdev）。（RK-A24, RK-A25, RK-A27, RK-A29）
5. **"硬件 crypto 引擎接进数据面"这件事有 x86/QAT 版本（RK-B12：XDP + QAT 内联 crypto，ISPA 2023），ARM SoC 版本为空。** 若用户想做"ARM SoC 数据面内联 crypto"，FYI 这是一个真实存在但未被移植的方向。
6. **未解决的口径问题**：引擎数字（1 MB 连续、DMA）与记录层负载（~16 KB record、逐块 AEAD、含握手）之间**无法换算**；`OPENSSL_armcap=0` 得到的"纯软件"基线数字在 RK3588 上**本次没抓到**（只拿到同族平台的 18–22× 比值）。这两项都需要用户自己在板上补测。

### 4. 对"把 RK3588 并入对比矩阵"的直接建议

**该扮演的角色（按价值排序）**

1. **边缘服务器本体 = "现实基线"（强烈建议）**。理由：它是这四类平台里**唯一一件真实在售的边缘产品形态**（4–12 W、2.5GbE、完整 Debian、8 核 A76/A55 + NPU），且 RK-B1 已经证明"三代协议在嵌入式上的能耗差异"是个能发的结果 —— 但**没人报过绝对吞吐与 CPU 占用**。用户要做的增量是：同一份内容、同一台 RK3588，跑 H1.1/H2/H3，报 **吞吐 / 每请求 CPU 时间 / 每字节能耗 / 整板功率** 四联表，并解释 RK-B1 观察到的"HTTP/3 更费能"在 SBC 上是否同样成立（注意：RK-B8 表明**实现差异会让 goodput 差 27%**，必须固定实现或用多实现交叉验证）。
2. **"硬件 crypto 引擎 vs ARMv8 指令 vs 纯软件"的三方受控对照（最有新意、成本最低）**。三条路径全在同一颗 SoC 上：
   - 纯软件：`OPENSSL_armcap=0`（OpenSSL 官方支持的开关，RK-A17）；
   - 指令：默认 OpenSSL（`gcm-aes-ce`，优先级 300）；
   - 引擎：cryptodev + librkcrypto（`/dev/crypto`）。
   输出 **AES-256-GCM / SHA-256 / RSA-2048 的吞吐 + CPU 占用 + 整板功耗**。**先验证据已经指向"引擎会输"（5.7× 与 ~28× 的差距）**，那么这篇的价值就落在"**为什么**"（DMA 往返 + 对齐/长度限制 + 优先级 0 的政策含义）与"**什么条件下会赢**"（大块连续、密钥不落地、低 CPU 占用场景）。**这是"批判性测量"而非"新加速器设计"，叙事要摆正。**
   ⚠️ 前提：必须用 **Rockchip vendor BSP** 内核（主线无 crypto 节点），并接受"vendor BSP 不可复现性"这个弱点；建议同时报告主线内核下的对照组。
3. **客户端/对端**：作为 FPGA / BlueField 侧实验的真实 ARM 端点（这正是本工作区既有《云游戏》与《WiFi 负载预测》选题里 RK3588 的用法）。
4. **反例/边界提供者（次要但有用）**：用它的失败与限制去**界定"L7 硬件卸载"的适用域** —— "连一颗有专用密码引擎的商用 SoC 都不值得把 TLS 卸给它"是一个有信息量的负结论，可加固用户整体论文的论证。

**可行的对比**：H1.1/H2/H3 服务端吞吐与能耗（2.5GbE 封顶，恰好是 SBC 的真实带宽）；三种加密路径的受控对照；AF_XDP/io_uring vs 内核栈的用户态网络对照（**先做可行性验证**，因为公开数字为零）；NPU 业务负载与网络栈抢 DRAM/功耗的竞争实验。

**拿它做不出来的**：数据面 RTL 卸载；HTTP 解析 / HPACK / QPACK 硬件实现；kTLS `TLS_HW` / `TLS_HW_RECORD`；10 GbE 线速；RSS/多队列分流；线速小包；**任何"我们给 SoC 加了一个协议栈加速器"的正文**（它没有可编程逻辑）。若论文的核心主张是"把 HTTP 栈搬进硬件"，RK3588 只能是**对照组**；若主张是"**在真实边缘节点上量化协议版本 × 加密路径的代价**"，RK3588 可以是**主平台**。

**一句话**：把 RK3588 放进矩阵时，**不要把它写成"第三种卸载载体"，要写成"第三种参照系"**——一个"硬件卸载在该平台上被证明不划算"的真实边缘节点，它的价值在**能耗/成本/现实性**这三个 FPGA 与 DPU 给不了的坐标轴上，而不在卸载能力上。
