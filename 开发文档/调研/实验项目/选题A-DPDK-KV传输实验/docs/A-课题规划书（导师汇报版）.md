# 选题 A 课题规划书（导师汇报版）

> 题目（暂定）：**面向 PD 分离 LLM 推理的 DPDK 用户态 KV cache 传输引擎**
> 一句话：在工业级 KV 传输引擎里落地一个 DPDK 用户态后端，用**端系统数据面成本**（每字节 CPU 代价与拷贝次数）而不是"能不能传"来定义贡献，并与该引擎自带的 TCP 传输后端同台对比。

## 0. 一页摘要

**做什么**：PD 分离（prefill/decode 分离）的 LLM 推理里，KV cache 要在实例之间搬运。目前在普通以太网卡上，这段搬运走的是内核 TCP 协议栈，每字节约 1–4 个核秒/GB 的 CPU 代价。本课题在工业级传输引擎 Mooncake 的 TENT 引擎里新增一个 DPDK 内核旁路后端，把这条路径换成用户态轮询收发 + 大页零拷贝，用**每字节 CPU 成本与拷贝次数**来度量收益，并在同一个引擎里与它自带的 TCP 家族后端、以及内核 TCP 做同台对比。

**为什么值得做**：① 部署现实——绝大多数数据中心没有 RDMA，而 KV 搬运已成为 PD 分离推理的系统瓶颈；② 有一个具体的产业标尺可以正面对比（该引擎自带高性能 TCP 后端）；③ 收益上限清楚，也能诚实说清上限在哪。

**不做什么（重要）**：不声称"普通以太网能传 KV"（已被占位）、不发明逐层流水调度（已被占位）、不主张带宽成倍提升、不主张替代 RDMA、不做 GPU 显存直通（消费级显卡不受支持）、不用云上虚拟网卡的数字冒充物理网卡结论。

**现在到哪了**：本机环境、上游版本锁定、引擎后端骨架与自建测试**已完成并有可复现证据**（详见 §6.1）；下一步是云上双节点真实数据面的端到端对照。

**需要什么**：两台按量云主机（单次实验 ≤ 50 元、月度 ≤ 300 元）＋ 一台可选的本机 Linux + 二手十万兆网卡（100–300 元，用于微基准）；以及导师对投稿目标与时间线的确认。

## 1. 研究背景与问题陈述

### 1.1 现象

大模型推理服务正在从"单机单实例"走向"prefill 与 decode 分离部署"：prefill 阶段算力密集、decode 阶段访存密集，两者分离能显著提升集群利用率。代价是——**KV cache 必须在实例之间搬运**。以常见配置估算，每 token 的 KV 字节数在几十 KB 到几百 KB 量级（Qwen2.5-1.5B 约 28 KB、7B 约 56 KB、Llama-3.1-8B 约 128 KB、Llama-2-7B 因多查询头更多约 512 KB），一次 4K 上下文的请求就意味着 0.1–2 GB 量级的数据搬家。

这段搬运不是"偶发的小流量"，而是**每个请求都会发生的、与算力并行的数据面负载**。它在生产栈里已经有专门的引擎（Mooncake 的传输引擎、vLLM 的连接器等），说明工业界已把它当成独立子系统来优化。

### 1.2 问题

在**普通以太网卡**上（这是绝大多数集群的现实），这段搬运走的是内核 TCP 协议栈，其成本主要不在带宽，而在：

- 每字节的**系统调用、协议栈处理与内存拷贝**（内核态收发 + 用户态 staging + GPU staging）；
- 在高并发、多对一的 **incast** 场景下的排队与尾延迟；
- 内核协议栈对 CPU 的占用与算力争抢（prefill 本身是算力密集的，搬运抢核会直接拉低推理吞吐）。

因此本课题的研究问题可以精确表述为：

> **在普通以太网卡上，能否通过端系统数据面（用户态网卡驱动 + 大页零拷贝 + 内核旁路）把 KV cache 搬运的每字节 CPU 代价与拷贝次数降低一个量级以上，同时不牺牲（甚至在 incast 下改善）尾延迟？**

这是一个**端系统数据面**问题，不是调度问题，也不是"能不能传"的问题。

### 1.3 为什么现在值得做

- **工业落地窗口**：生产栈已经把 KV 传输做成独立引擎并支持多后端（同仓库内就有多条可替换的数据面实现），新后端可以以"插件"方式进入，不需要改动推理框架与连接器——集成风险低、可对比性强。
- **学术空白位置明确**：已有工作分别占住了"用普通以太网传 KV 的动机"与"逐层流水掩盖传输"，但**端系统数据面本身的每字节成本**这个问题，在 KV 传输语境下还没有被系统性地做进生产栈并以同台对比的形式给出。
- **可证伪**：收益可以被一个明确的失效条件推翻（链路充裕且内核启用分段卸载卸载时，收益趋近于零）。这使课题本身是科学的，而不是工程宣传。

## 2. 研究问题与贡献边界

### 2.1 计划主张（可宣称）

| # | 主张 | 度量口径 |
|---|---|---|
| C1 | 每 GB 的 **CPU 成本**与**拷贝次数**相对内核 TCP 显著下降（文献口径为 10–250× 量级，需自测复现） | 核秒/GB；拷贝次数（按代码路径计数） |
| C2 | 在高并发/多对一（incast）场景下**尾延迟**改善（p99、p99.99） | p50/p99/p999/最大延迟 |
| C3 | 与生产引擎自带 TCP 家族的**同台对比**与"成本—性能 Pareto 位置" | 同一基准、同一硬件、同一负载 |
| C4 | **KV 语义驱动**的机制贡献（块级确认、信用流控、优先级），而非通用网络优化 | 机制有效性 + 端到端指标 |

### 2.2 明确不主张（不可宣称）

- 不主张**带宽成倍提升**：链路受限时通常只有 1.0–1.3×，带宽不是本课题的卖点。
- 不主张**替代 RDMA**：RDMA 仍是上限参照，我们主张的是"普通网卡上的可用性"。
- 不主张**绝对推理吞吐**（tokens/s）：除非有大模型真机数据，否则越界。
- 不主张 **GPU 显存直通/真零拷贝到显存**：消费级 GeForce 不在厂商支持范围，这条只能作为上界参照或 future work。
- 不主张**逐层流水调度**为创新点（已被占位），只作工程化复用。
- 不把**云上虚拟网卡的微基准数字**当作物理网卡结论。

### 2.3 收益上限的诚实估算

端到端改善近似为 `改善 ≈ p × s`：`p` 是传输耗时占请求端到端时间的比例（据选型核算取 `p ∈ [0.2, 0.42]`），`s` 是传输耗时自身的下降比例（乐观取 `s ∈ [0.1, 0.5]`）。据此端到端改善大约落在 **2%–21%**。这个区间**不小但也不夸张**——它正说明本课题的价值主要在数据面成本与尾延迟，而不是"让推理快几倍"。这一点我会在论文与答辩里从第一句就讲清楚。

## 3. 与已有工作的关系（差异化定位）

| 已有工作 | 它占住了什么 | 本课题怎么写 |
|---|---|---|
| Mooncake TENT 自带 TCP 家族 | "数据中心 TCP 上的 KV 传输引擎"（内核 socket、持久连接、分片、逐次确认） | 强调我们替换的是**数据面操作系统路径**（用户态轮询 + 大页零拷贝 + 内核旁路），并且以**引擎新后端**的形式与它**同台对比**，而不是另起炉灶 |
| PrfaaS 类工作 | "在普通以太网上传 KV 且去 RDMA"的动机 | 承认其调度层贡献，明确我们的贡献在**端系统数据面**，不在"能不能传" |
| Topology-Aware 类工作 | 逐层流水调度掩盖传输 | 逐层流水只作**工程化复用**；我们的增量在该流水**运行于轮询模式网卡时的实现** |
| 面向 RTT/带宽边界的分析工作 | 指出逐块串行在高 RTT 下退化 | 引用其诊断作为动机，我们回答它**留在数据面**的问题（每字节成本与拷贝） |
| 内核旁路/用户态网络栈的经典工作 | 每包 cycles 等微基准口径 | 复用其度量口径，但把场景换成 **KV 传输**，并用端到端与 incast 尾延迟补充 |

一句话差异化：**把 DPDK 做进工业级 KV 传输引擎，用每字节 CPU 成本与拷贝次数定义贡献，并与生产栈自带的高性能 TCP 后端正面同台。**

## 4. 技术路线（方法学层）

### 4.1 集成点选择：引擎后端（而非推理框架连接器）

两条可选路线：**(A)** 在推理框架侧写一个自定义 KV 连接器，数据面自己造；**(B)** 在传输引擎里新增一个数据面后端。

选 (B) 的理由（也是任务可行性的核心）：

- **接口面窄**：只需实现一个后端类（一组固定的生命周期与提交/查询/注册接口），而 (A) 要自造完整传输栈。
- **引擎已提供的能力直接复用**：持久连接/通道管理、子批次调度、失败切换（failover）、内存注册路径——这些是工作量的大头，(B) 不需要重写。
- **自带生产级对照基线**：同一个引擎里就有它自家的 TCP 家族后端，同台对比是天然成立的（这正是论文最需要的东西）。
- **推理框架零改动**：引擎已提供运行时开关，切换数据面不需要动推理框架与其连接器，端到端链路天然打通。

风险与备用方案：引擎是较新的子系统，上游演进快。应对是**锁定到具体提交**（已做），并把 (A) 作为备用集成点——若集成在 2–3 周内跑不通，就把同一份传输实现改挂到推理框架的连接器上（同一引擎、两个集成口，不是两套工程）。

### 4.2 数据面设计要点

```
   应用层（推理引擎 / KV 连接器 / 基准工具）
              │  提交"把这段本地内存传到对端这段内存"
              ▼
      KV 传输引擎（版本锁定；负责分片、调度、重试、失败切换）
              │  后端插件位（本课题新增）
              ▼
   ┌──────────────────────────────────────────┐
   │ 本课题的 DPDK 后端                        │
   │  · 用户态轮询收发（内核旁路）              │
   │  · 大页内存 + 外部缓冲注册（减少拷贝）      │
   │  · 块级确认 / 信用流控（KV 语义驱动）       │
   └──────────────────────────────────────────┘
              │  PMD（用户态网卡驱动）
              ▼
        普通以太网卡  ───────  普通以太网卡
              ▲                    │
              └──── 对端同构 ───────┘
```

四个设计要点（方法学层面）：

1. **内核旁路**：数据面完全在用户态完成收发，移除系统调用与协议栈处理。
2. **内存路径**：大页内存 + 外部缓冲注册，目标是把"每字节约一次拷贝"降到"零拷贝或一次必要拷贝"；GPU 侧只做 staging（不做显存直通）。
3. **KV 语义机制**：KV 块是**有界、可编号、可丢弃（有前缀依赖但不是全部必需）**的——这允许做块级确认、信用流控与优先级，而不是照抄通用 TCP 语义。这是 C4 的来源。
4. **逐层流水**：推理框架本身有逐层钩子，我们复用为"传输与计算重叠"的手段（非创新点），但要处理它在轮询模式网卡下的实现细节。

### 4.3 为什么用普通以太网卡（选题的现实意义）

RDMA 方案的性能上限更高，但需要专用网卡、无损以太网配置与更复杂的运维；在大量存量集群里，"普通以太网 + 更低的端系统成本"是可部署的中间路线。本课题不挑战 RDMA 的上限，而是把"普通网卡上的每字节成本"这一维度做扎实。

## 5. 实验设计

### 5.1 链路档位与选型判据

- **默认档位：10 GbE**（或用流量控制限速到 1 / 2.5 / 5 Gbps 做敏感度）。25/100 GbE 只作补充——链路越宽，传输耗时占端到端比例 `p` 越小，越测不出数据面差异。
- **选型判据**：按 `p ∈ [0.2, 0.5]` 选模型与链路组合，保证"传输既不是微不足道、也不是压倒一切"。这一判据已在项目内的选型核算里给出可复算的公式与数值。

### 5.2 负载矩阵（模型 × 数据集）

| 角色 | 模型 | 数据集 | 说明 |
|---|---|---|---|
| 本地正确性闭环 | Qwen2.5-1.5B | ShareGPT 到达过程 | 本机单卡可跑，验证"KV 真从 A 传到 B 并被 decode 用上" |
| 形态现实性（主实验） | Qwen2.5-7B / Llama-3.1-8B | ShareGPT + LMSYS-Chat-1M | 覆盖分组查询注意力（GQA）形态 |
| 链路压力（暴露瓶颈） | Llama-2-7B（KV 更重）或 Qwen2.5-32B | LongBench / RULER 长输入 | 让传输占比 `p` 变大 |
| 满线速与扫参 | **合成 KV**（按模型配置的几何生成） | 由到达过程驱动 | 见 §5.3，这是满线速实验的唯一可行方式 |
| 大体量形态（不真跑） | 70B 级架构（哑构造） | 合成 trace | 只做参数化外推，标注为外推 |

### 5.3 一个必须提前讲清的前提：单张消费级 GPU 喂不满链路

按 KV 几何与链路带宽反算：打满 10 GbE 需要 Qwen2.5-1.5B 约 4.4 万 token/s（对应约 134 TFLOPS 的 prefill 算力），或需要 KV 更重的 Llama-2-7B 约 2,400 token/s（约 32 TFLOPS）——单张消费级显卡都达不到。**因此"满线速"实验必须用合成 KV 流**（按几何生成的字节流，由到达过程驱动；打满 10 GbE 只需每秒数千个 256 KB 块，单核内存带宽即可）**；真实模型只用于正确性闭环与亚线速的端到端指标**。这一条会写进论文的实验设置，避免"数据不可信"的质疑。

### 5.4 消融矩阵

KV 精度（FP16 / INT8 / INT4）× 块大小（64 KB / 256 KB / 1 MB）× incast 度（1 / 4 / 16）× 内核分段卸载开关（TSO/GSO）× 传输后端（内核 TCP / 引擎自带 TCP 家族 / 本课题后端，可选 AF_XDP 旁路纯度消融与 eRDMA 上限参照）。

### 5.5 对照组设计

| 组 | 实现 | 作用 |
|---|---|---|
| ① | 内核 TCP（基准工具 + 推理原生路径） | 最低基线 |
| ② | 引擎自带 TCP 家族（生产级对照） | **主对照**，同台对比 |
| ③ | 本课题 DPDK 后端 | 待验证对象 |
| ④（可选） | AF_XDP 半旁路 | "旁路程度 × 收益"消融，也降低他人复现门槛 |
| ⑤（可选） | 云上 eRDMA | RDMA 上限参照 |

### 5.6 指标口径（唯一口径，禁止另立）

每 GB CPU 成本（核秒/GB）、传输耗时占请求端到端时间的比例、首 token 延迟（TTFT）、每 token 输出延迟（TPOT）、满足 90% 服务目标的吞吐（goodput@SLO）、p50/p99/p999、KV 传输字节数、有效带宽。大消息口径统一到"传完一个请求的 KV 段"。

### 5.7 公平性红线（评审最可能攻击的点）

- **必须同时报告内核 TSO/GSO 开与关两组数字**：文献值显示，内核开着分段卸载时其每 GB CPU 成本会塌缩一个数量级，**结论会翻转**。只报关闭态是不公平对比，只报开启态则会淹没本课题的收益。
- **微基准只在物理网卡上做**：云上的网卡是 SR-IOV 虚拟功能（设备号形如 `0000:00:06.0`），其每包开销与物理网卡不是一回事；云上只做两节点端到端与对照。
- **轮询模式要报能效与 CPU 占用**：轮询线程可能占满核，需用中断-等待混合模式并同时报 CPU 成本与能耗。

### 6.2 未来里程碑与 Go/No-Go

| 时间 | 目标 | Go/No-Go 判据 | 退路 |
|---|---|---|---|
| 2026-10 上 | 云上环境：单节点跑通内核旁路工具栈 → 双节点互通 | **G1**：跑不通 → 退 AF_XDP 半旁路或纯仿真 | AF_XDP 门槛更低（不需绑定驱动）、云上可复现 |
| 2026-10 下–11 | 后端骨架打通接口语义 | **G2**：2–3 周内跑不通 → 退到推理框架连接器集成点 | 同一份传输实现换集成口 |
| 2026-12 | 真实网卡跨主机收发 + 零拷贝（外部缓冲）+ 信用流控 | 吞吐/CPU 达成预期一半以上 | 若收益不足，主线转向 KV 语义调度 |
| 2027-01 | 逐层流水 + incast 场景；与自带 TCP 家族首轮对比 | **G3**：收益不显著（< 2×）→ 主线改为"KV 语义调度（信用/优先级/incast）" | 收入机制贡献章节 |
| 2027-02~03 | 端到端（TTFT/goodput）+ 全部消融 + 合成 KV 满线速 | 数据齐备，含 TSO/GSO 对照 | — |
| 2027-04 | 写作投稿 | 投稿前三条硬条件自检 | 依审稿意见迭代 |

## 7. 资源需求与成本

| 项 | 需要 | 用途 | 成本量级 |
|---|---|---|---|
| 本机（已有） | Windows + 子系统 Linux、6 核 12 线程 / 32 GB / 消费级显卡 | 代码开发、正确性闭环、虚拟收发路径验证 | 0 |
| 云主机 × 2 | 按量付费、同 VPC 同可用区、第六代及以后、8 核 16 GB 级 | **双节点端到端与后端对照（唯一有外部效度的数据来源）** | 单节点约 1–2 元/小时；单次实验 ≤ 50 元、月度 ≤ 300 元 |
| 二手双口十万兆网卡（可选） | 约 100–300 元 | 本机物理网卡的**微基准**（每包开销、投递时延） | 一次性 100–300 元 |
| 云上 eRDMA 实例（可选） | 与同规格实例同价 | RDMA 上限参照 | 视对照轮次 |

成本纪律：按量实例**跑完立即释放**（关机不等于停费）；每轮实验在记录卡写明**实际花费**；超预算先确认；长实验不用抢占式实例（随时被回收）。

人力节奏（建议，待与导师确认）：每周固定 8–12 小时投入；关键路径是"云上双节点打通 → 跨主机数据面 → 端到端对照"，其余（仿真、参数化、写作）可并行。

## 8. 风险、反例与退路（诚实清单）

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **内核分段卸载（TSO/GSO）开启时收益塌缩** | 结论可能被质疑"选了个不利的内核配置" | 两组都报；把"何时收益为零"作为失效条件明确写出，反而增强可信度 |
| R2 | 云上是虚拟网卡，**微基准数据不可用** | 每包级结论缺数据 | 微基准留给本机物理网卡（可选买卡）；云上只做端到端与对照 |
| R3 | 上游引擎演进快 | 不可复现 | 已锁定到具体提交；月度做一次上游差异审计 |
| R4 | 端到端收益被摊销（`p × s` 只有 2%–21%） | "提升不大"的质疑 | 把主张限定在数据面成本与尾延迟，端到端作为补充；并给出 `p` 的可测量方法 |
| R5 | 轮询线程占满 CPU | 抢算力、能效差 | 中断-等待混合模式；同时报 CPU 成本与能效 |
| R6 | 当前后端仅单机回环 | 跨主机结论缺位 | 明确作为下一阶段增量（12 月里程碑），不在现阶段包装成已具备 |
| R7 | 逐层流水/普通以太网动机**已被占位** | 创新点被质疑 | 全程只作工程化复用与动机引用（§2.2、§3） |
| R8 | 虚拟功能在宿主机维护时消失 | 长测中断 | 带重连与重试；长测避免依赖单次会话 |
| R9 | 云上成本失控 | 预算超支 | 先写脚本再开机器；跑完立即释放；单次/月度预算上限 |

**退路**：① 集成跑不通 → 换到推理框架连接器集成点（同一实现）；② 内核旁路在本环境不可行 → 退 AF_XDP 半旁路（仍有"旁路程度 × 收益"的消融价值）；③ 收益不显著 → 主线转为 KV 语义调度（信用流控/优先级/incast），仍是完整贡献。

## 9. 预期产出与投稿目标

**产出**：

1. 一篇系统论文：**端系统数据面成本**为核心主张，与内核 TCP + 生产引擎自带 TCP 家族正面同台，附端到端（TTFT/goodput）与 incast 尾延迟。
2. **可复现的实验代码与数据**（后端实现以补丁形式开源、基准脚本、参数表、原始日志）。
3. 一次与生产栈的正面比较（工业界可直接采纳的后端）。

**投稿目标（依 CCF 第七版推荐目录）**：

- 期刊（B 类）：Computer Networks、IEEE TCC、JPDC。
- 会议（B 类）：ICDCS、ICPP、Euro-Par、MSICC 系列（ICCD/ICCAD/DATE）、CoNEXT、ICNP、IWQoS。
- 注意更正：ACM TOS / ACM TACO 是 **A 类**（不能当 B 类目标写）；IEEE TNSM 与 Computer Communications 是 **C 类**。

**投稿前三条硬条件自检**：① 与内核 TCP + 至少一条 RDMA/UCX 正面对比且报端到端指标；② 有 KV 语义层的机制贡献；③ ≥ 3 场景 × ≥ 3 基线 + 参数表 + 开源代码。

1. **方向与边界**：是否认可"端系统数据面成本"作为核心主张、以及 §2.2 的"不可宣称"清单（尤其是不主张带宽提升、不做 GPU 显存直通）。
